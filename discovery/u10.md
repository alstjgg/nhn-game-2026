## 1. Invariant-vs-reference deviation applied (P0-A precedence)

`docs/design/phase2-ui/index.html` (head) loads the three families from
`fonts.googleapis.com` / `fonts.gstatic.com`. spec-client §3 inv 10 forbids any
third-party request, so u10 ported the **compliant equivalent** instead of the
reference's own markup: the same eleven family/weight/style faces, the same
per-`unicode-range` slicing, vendored under `public/assets/fonts/` and declared
by `src/client/styles/fonts.css`. The reference file itself is untouched.
`docs/design/phase2-ui/README.md` lines 90–93 asks for exactly this.

## 2. Upstream slices are **not** disjoint — the partition is ours

`tests/assets/unicode-range-coverage.test.ts` requires the slices of one Korean
family/weight to be non-overlapping. Google's own sheet is not: each Korean
weight ends with a "most common glyphs" slice (ASCII + ~30 high-frequency
syllables) and a `latin` slice that both re-declare codepoints the numbered
block slices already carry; the CSS cascade resolves each codepoint to the
*last* face that claims it.

`tools/fonts/vendor-google-webfonts.mjs` therefore bakes that cascade into the
declarations — walking each family/weight backwards, a face keeps only what no
later face claimed. Coverage is byte-for-byte the upstream coverage; the
declarations are a true partition. Worth knowing at integration: this is a
deliberate divergence from upstream's literal `unicode-range` strings, and
re-running the vendor script is the only supported way to regenerate them.

## 3. Seam friction — nothing mounts `styles/index.css` yet, but `dist/` must carry the sheet

`tests/assets/no-third-party-url.test.ts` c5(b/c) requires the **built** output
to contain a stylesheet with `@font-face` + `unicode-range`. Nothing imports
`src/client/styles/index.css` today (the boot root still renders u0's
placeholder), so no skin CSS reaches the bundle at all.

The two obvious fixes both break `e2e/fonts.spec.ts` "load budget": that spec
injects its **own** probe copy of every `@font-face` via `addStyleTag`, so if
the document already declares the same faces, Chrome loads *both* FontFace sets
and every slice is fetched twice — measured 26 slices / ~490 KB against budgets
of 24 / 300 KB. Linking the sheet from `index.html`, importing it from
`main.ts`, or importing `index.css` from `main.ts` all trip this.

u10 therefore ships the sheet the way a self-hosted font pack normally ships
it: `public/assets/fonts/fonts.css`, generated by the same script, addressing
its slices **relatively** so it is correct under any `base` and needs no build
step. `src/client/styles/fonts.css` stays the bundler-side sheet (root-relative
urls, which Vite rebases) and `styles/index.css` imports it, ready for whoever
mounts the skin.

**For u1 / u11 / the integrator:** once the skin is actually mounted, the
document *will* declare these faces and the "load budget" probe will
double-count. That spec needs to switch from `addStyleTag` to measuring the
page's own faces at that point — u10 must not pre-empt it.
