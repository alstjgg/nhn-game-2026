## The surface this suite pins (TEST agent's call, absent a design doc)

`src/engine/state/index.ts` — created here as a **signature stub only**
(throwing bodies, e0's convention), so the RED is per-test rather than one
import error, and so IMPLEMENT inherits a fixed contract:

```ts
initState(characters: Characters): RunState
applyEffects(state: RunState, effects: Effects, cause: string): DeltaEntry[]
renderSymptoms(journal: DeltaEntry[], pack: Symptoms, owners?: SymptomOwners): string[]
```

Three choices inside that are mine, not the spec's:

- **`applyEffects` mutates `state` in place and returns only that
  application's journal slice.** The spec's §4.2 vocabulary ("apply … → record
  journal") reads as mutation, and e3 owning the beat loop wants an accumulator
  it appends to. An immutable `(state, effects) => {state, journal}` would
  satisfy the same spec text; if e3 needs that, this is the seam to change.
- **`initState` takes `Characters` alone.** `clock`/`route.node` seeding is
  left unasserted (`route.beat` 0 and `route.visited` `[]` are asserted) —
  §1.1 gives `route` no initial node and the gate graph is out of scope (§8).
- **`{who}` substitution takes an injected `variable → name` map** rather than
  reading `characters.json` inside the renderer. §2.2 defines the lookup as
  "the `name` of the character whose `meters[].variable` matches", but making
  the renderer take a `Characters` argument would put pack-walking inside a
  lookup function. The shipped 우는다리 `symptoms.json` contains **no `{who}`**
  at all (sentences say 발신자 literally), so nothing in the real pack exercises
  this path today.

## Ambiguities resolved against the spec, worth a reviewer's eye

- **"the three hard errors" is a mis-count in the source.** §2.3 closes with
  "All three hard errors (2, 3, 7) … coverage (2) · `min` descending (3) · no
  digits (7)", but rule 3 is the *sort key* and the `min`-descending sentence
  lives in rule 2, which says the opposite of a runtime check: "The renderer
  **trusts** that the array is already authored in `min` descending order and
  does not defensively sort … the only basis for that trust is lint (§6-2)."
  Two readings, and they are mutually exclusive at the test level. This suite
  takes the explicit one — **a mis-ordered array is rendered by iteration
  order, not re-sorted and not thrown on** (test 10) — because it is stated as
  behaviour, and because the unit's own AC lists exactly two throws ("a single
  digit anywhere in the output throws · no symptom match throws"). If the panel
  rules the other way, test 10 is the single test that flips.

- **§2.3-7 is scoped to *the output*.** A fourth entry removed by §2.3-4's
  truncation never reaches the returned array, so a digit in it cannot violate
  I12 (test 30). Literal reading; the alternative (scan every candidate before
  truncating) would make the error depend on entries the player never sees.

- **`min` is inclusive.** "the **minimum magnitude** `|after − before|` at which
  this sentence applies" — magnitude 15 matches `min: 15` (test 8). Not stated
  as an operator anywhere, and the §2.2 worked render only exercises the strict
  case (25 ≥ 20).

## Left untested on purpose — open questions for IMPLEMENT / review

- **Whether `applyEffects` rejects a `0` or fractional delta.** §1.3 calls both
  authoring errors and §6-2 lint preempts them, but §2.3-1 *requires* the
  journal to be able to carry magnitude-0 entries ("the entry stays in the
  journal"), so a throw inside `applyEffects` would contradict the renderer's
  own premise. Nothing asserts either way; the renderer's side of it is
  covered (tests 4–6, 14).
- **Where a magnitude-0 journal entry actually comes from.** §2.3-1 says "the
  only traffic on this path is multiple deltas cancelling out", but two
  cancelling `±5` applications produce two entries of magnitude 5, not one of
  0 — unless the journal is collapsed per variable per beat somewhere. That
  collapse is not in §2.1, §2.3 or §4.2. e3 (beat driver) is the likelier
  owner; flagged rather than invented here.
- ~~**A flag written to the value it already holds** (`before === after`).
  §2.3-1's drop rule is written for `magnitude === 0` and "flags have no
  magnitude", so a no-op flag falls through to §2.3-2's hard error. Almost
  certainly wrong, but the spec does not say, so no test pins it.~~

  **CLOSED in final-PR review (#116, finding F).** The shipped behaviour turned
  out to be neither of the guesses above: a `true → true` write reached §2.3-2
  and *matched*, so it rendered its `set` sentence and the player was shown a
  change that had not happened. Resolved by extending §2.3-1's drop to flags —
  a reading of the rule's stated REASON rather than of the arithmetic it is
  phrased in: "state did not move, so there is no symptom to show". The
  arithmetic (`magnitude === 0`) could only ever reach scalars, because the same
  paragraph says flags have no magnitude, so the omission is a gap in the
  wording rather than a deliberate exclusion; every other clause of §2.3-1
  transfers verbatim (the entry stays in the journal — §2.1 records *attempts*;
  and the drop is a stage BEFORE rule 2's hard error, so an unauthored `unset`
  is unreachable by a write that never happened).

  Why it was worth closing rather than re-flagging: the 우는다리 pack's own idiom
  has G3 and G5 each asserting one flag from two buckets, so it is one authoring
  edit from firing, and §6-2 lint is static — it cannot see which pair of
  buckets a given run visits. Pinned by five tests in
  `tests/engine/state/render-symptoms.test.ts`, including the
  two-buckets-one-flag journal.

## `{who}` substitution is unwired — deferred, not fixed (r1 finding A, round 2)

`src/engine/index.ts:180` calls `renderBeatSymptoms(entries, symptomsPack)` with
no `owners` argument, so `{who}` is never substituted. On spec-engine §2.2's own
canonical `symptoms.json`, `SCENE_SYMPTOMS` is
`["{who}가 한 박자 늦게 답했다"]` — the literal placeholder reaches
`compose.ts` and ships into the proxy prompt. Reproduced at `46348e0`; a
`git log -S'{who}'` over this run's commits returns nothing, so no unit ever
touched it.

**Why it is deferred rather than fixed here.** Wiring it needs an owner map the
engine does not currently hold: §1.1a settled that NPC meters beyond the bound
pair are authoring annotation and *not* engine state, so "who owns this
variable" has no home in the state core, and inventing one would be a signature
change against e0's frozen surface (decision 14) taken during a review round.
The reviewer's own position: *"one line of deferral record resolves this — I am
not asking for the feature."*

**What it costs today:** nothing renders, so no player sees it; but the first
live Bedrock call would send a literal `{who}` into the Call 2 prompt. That
makes it a prerequisite of the live-provider run, alongside
[e9 §9](./e9.md) (a fallback run is currently unrecordable). Both need a
decision that this run's frozen inputs put out of reach.
