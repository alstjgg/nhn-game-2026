# e9 — discovery

## 1. D-0 is resolved at this base — e7 **did** merge

`design.md` §0 was written against a base where `src/driver/index.ts` still
stubbed everything, and planned for `runHeadless` to compose the leaf modules
itself. That is no longer the situation: `super/e7` merged (`64d42af`), so
`createLiveDriver` — the real beat ordering, the two feed flushes, the `waiting`
brackets, the fallback branch — is what drives this run. `tools/driver/run/bind.mjs`
calls it and supplies nothing but adapters.

What is still missing is the **engine factory**: `src/engine/index.ts`
`createEngine` remains `throw new Error('unimplemented: createEngine')`, and
`EnginePort` (`src/driver/ports.ts`) is a wider surface than `Engine` anyway.
So `bind.mjs` assembles an `EnginePort` over the three merged leaves —
`createBeatDriver` (beat chain, views, routing), `initState`/`applyEffects`/the
symptom renderer (state core), `buildFeed`/`buildReportSentences`/
`assembleExperienced` (feed) — through the ports those modules already declare
(`StateCorePort`, `RoundAssemblerPort`, `BeatPack`).

**Steer candidate.** That assembly is a *product* concern, not a tool's: the
browser bundle will need exactly the same object. When the unit that implements
`createEngine` lands, `createEnginePort` in `bind.mjs` should collapse into it
and this file should keep only the `createLiveDriver` call. Until then there is
one binder, in one file, behind one function — deliberately, so the collapse is
a deletion rather than a merge.

## 2. Two decisions the contract does not make, made here

**`beats[].beat` is 1-based.** `src/engine/beat/schedule.ts` indexes the schedule
from 0; `run-record.schema.json` pins `beat` to `integer, minimum 1`. The port's
`current()` offsets by one on the way out, so the offset is applied once, at the
recorder's edge, and the same number reaches `beat_start`, `fallback` and the
record. Nothing downstream of the port ever sees the 0-based index.

**`reports` is the last round's Call 3 payload.** The schema has one `reports`
object; 우는다리 has seven gates and therefore seven rounds and seven Call 3s.
The record keeps the last. This is under-specified in
`contract-run-artifacts.md` §1 ("the two reports (W1/W3)") — if the metric stage
wants per-round reports, the schema needs an array and that is a schema change,
not a recorder change.

## 3. A third thing on the stream: the `gate_stance` annotation

The spec names two seams. `beats[].gate` / `beats[].stance` are reachable from
neither on its own: the `ViewEvent` union carries no gate id and no stance, and
the transport sees a stance with no idea which beat it belongs to. The binder
therefore writes one annotation — `{type:'gate_stance', beat, gate, stance}` —
into the same array, at the moment Call 1 returns, and `reduceEvents` folds it
in. It is a *pairing* of the two seams, not a third source: both fields come
from the driver's cursor and the Call 1 body respectively.

If the seam ever grows a `gate` field on `beat_start`, this annotation is the
line to delete.

## 4. Schema collisions (both STEER candidates)

**`beats[].deltas[].before/after` is `number` in the schema, `number | boolean`
in the engine** (`src/engine/beat/ports.ts` `DeltaEntry`). Flag deltas
(`tip_traced`, `originals_read`, …) are journal entries like any other, and
dropping them would cost exactly the attributability the journal exists for. The
recorder coerces `true`/`false` to `1`/`0` at the serialization boundary. The
better fix is to widen the schema to `["number","boolean"]` —
`data/runs/_schema/**` is frozen for this unit. *Not exercised by the committed
sample:* the fixture provider always picks the first stance, and none of
우는다리's first-stance outcomes sets a flag.

**e8's walker was missing three keywords the run-record schema uses** — array
form `type`, `enum`, and `$ref` → `#/$defs`. A walker that reports a keyword as
*unimplemented* and passes the value anyway is vacuous, so
`tests/runloop/schema.ts` was extended additively (`$defs` annotated, `enum` and
`$ref` enforced, array-`type` treated as an implicit union, root threaded for
pointer resolution). e8's own meta-state suite still sees `unimplemented: []`.

*Directional smell:* a shipped tool now imports `tests/**`. The walker should be
promoted to `tools/lib/` or `src/shared/` by a later unit; decision 1's "import
it rather than write a second one" is the stronger constraint today.
**Resolved in review — see §11:** the smell was a defect. The walker moved to
`tools/driver/run/schema.ts`; `tests/runloop/schema.ts` re-exports it.

## 6. The fixture echoes its input into `reports.facts`

`createFixtureProvider`'s reporter returns `request.slots.EXPERIENCED` as
`facts`, and `EXPERIENCED` legitimately carries the gate's `inner_note` (contract
§5). The committed sample record therefore shows `[속내] …` inside
`reports.facts`. That is the fixture being a mirror, not a seam leak — the
view-driver guard covers the driver's out-edge and this artifact is not on it —
but a reader of the sample should not mistake the echo for report content.

## 8. `mined_from_run` — provenance is read off the id (review finding B)

The first cut wrote `block.mined_from_run ?? null` over a `Block` that is
`{id, text}` and nothing else, so the `??` branch was **structurally dead**:
`cloneMetaState` rebuilds blocks from those two fields, and
`meta-state.schema.json`'s `carried_blocks.items` is `additionalProperties:false`,
so the property could never arrive. Every record therefore asserted `null` —
which `run-record.schema.json` documents as *"mined from the script timeline"* —
for blocks that a previous **run** had minted. A definite wrong answer.

`mined_from_run` is `required` in the frozen run-record schema, so the field
cannot simply be dropped. It is now derived from the id, which is where the
provenance actually lives (`src/shared/id.ts`: `b-r<run>-<channel><nn>` for a
minted sentence, `t<n>` for an authored script event):

| id family | `mined_from_run` |
|---|---|
| `t<n>` (authored script event) | `null` — the schema's documented meaning, now true |
| `b-r<N>-…` (minted) | the archived `run_id` whose `-r<n>` suffix is `N` |
| neither, or `N` absent from `report_archive` | **throws** — the recorder does not guess a run id |

**STEER candidate (the end-to-end fix).** The honest carrier is the type, not
the id: `Block` (`src/shared/contracts.ts`, frozen here) would grow a
provenance field and `meta-state.schema.json`'s `carried_blocks.items` would
carry it across runs. Both files are frozen for this unit, so the id-derived
lookup stands in. Its one weak spot is the suffix match: a run recorded with
`--run-id=<something-without--r<n>>` cannot be matched, and that case throws
rather than guessing.

## 9. A failed Call 3 makes the run unrecordable (review finding C)

`reports.report_body` has `minLength: 1` in the frozen schema, and the record's
reports are the Call 3 payload **verbatim** (A12 — rejoining the segmented
`Sentence[]` is banned). So a run whose reporter call fell back has no report to
record and no legal record: `assembleRecord` used to fabricate
`{"facts":[],"report_body":""}`, which the repo's own walker rejects, and the
CLI wrote it anyway because the write sat outside the `--validate` branch.

Both halves are closed: the fabrication throws, and *every* write is validated
regardless of `--validate` (the flag now only reports conformance in the summary
line). **STEER candidate:** stage 6 will want the fallback run recorded rather
than refused — that needs `reports` to be nullable in `run-record.schema.json`,
a `data/**` change this unit may not make.

## 10. The committed sample is now compared, not overwritten (review finding D)

`tools/tests/run-record.mjs`'s A1 test used to invoke the CLI with no `--out`,
so `npm run check` rewrote the tracked `artifacts/runs/우는다리-fixture-r1.json`
in place and then asserted the file existed — self-confirming. The test now
writes to a temp dir and byte-compares against the committed record.

This makes the sample a **golden**, which decision 9 explicitly said it was not.
The reviewer's point wins: an artifact no test compares against is evidence of
nothing. The consequence is that a deliberate change to engine output now fails
this test until the sample is regenerated — which is the default CLI invocation
(`node tools/driver/drive-run.mjs --pack 우는다리 --provider fixture --validate`),
and the failure message says so.

## 11. The walker moved out of `tests/` (review finding E)

§4's "directional smell" became a review finding: a shipped CLI cannot import
from the test tree (`cp -R src tools data /tmp/ship && node tools/driver/drive-run.mjs`
died on `ERR_MODULE_NOT_FOUND: /tmp/ship/tests/runloop/schema.ts`). The walker
now lives at `tools/driver/run/schema.ts` and `tests/runloop/schema.ts` is a
one-line re-export of it — one definition site, and the import direction is
tests → tools rather than tools → tests. `tools/lib/` would be the better home
still, but it is frozen for this unit.

`tools/**` is in no tsconfig, so the walker is typechecked only because
`tsconfig.test.json` reaches it transitively through that re-export. Adding
`tools` to a tsconfig `include` is the real fix and `tsconfig*.json` is frozen.
