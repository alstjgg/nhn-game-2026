## VERIFY attempt 1 — findings not fixed inline

1. **The P0-B capture protocol and the boot sweep are in conflict (u11's own,
   fix next attempt).** `shell.css:172` hides every `.win` behind
   `body.booting`, and the class is dropped by a timer that
   `page.clock.install()` freezes. `e2e/captures.spec.ts` installs the clock
   before the sweep has passed, so all ten build shots render an empty desk.
   Measured under the spec's own protocol: `body.className === "booting"`,
   every `.win` `visibility:hidden` with a non-zero box. The unit-level lesson
   worth carrying past u11: *element-count and bounding-box guards cannot detect
   a blank shot* — `visibility:hidden` keeps both — and the C15 "clipped
   fallback" converts Playwright's one honest signal (a refused element
   screenshot) into a silent pass. Any future capture spec should assert
   computed `visibility` and the absence of `booting` before it shoots.

2. **`e2e/red-thread.spec.ts:201` is time-flaky under full-suite load (owner
   u8's mechanism, u11's gate).** `pathData()` came back empty one line after
   `toHaveCount(1)` passed, because the fixture run keeps ticking between the
   two reads and [u8#c3] correctly clips a thread whose anchor left the visible
   rect. Reproduced once in ~4.3 min of full-suite load, never in isolation
   (3× single, 1× whole file, 1× full re-run all green). Seam friction, not a
   product bug: the desk offers no "hold still" handle to a spec that needs two
   geometry reads in the same state — `__shell.drain()` releases work rather
   than pausing it, and `__feed.rate()`/`seek()` move the clock forward only.
   A `pause()`/`resume()` on the driver handle would let every geometry oracle
   in the suite stop guessing.
   **↳ CORRECTED 08-04 by u11 attempt 2 — see the attempt-1 close-out section at
   the end of this file, item 2: `__feed.rate(0)` IS that pause. The finding
   survives only as a discoverability complaint, not as a missing handle.**

3. **`git diff --name-only super/…...HEAD` for u11 touches nine files outside
   its declared `file_globs`** (`playwright.config.ts`, `src/client/debug/pane.{ts,css}`,
   `src/client/driver/index.ts`, `e2e/{a11y,debug-pane,fonts,red-thread,reports,run-loop,shell}.spec.ts`).
   Every one is annotated `C17 / [u11#c12] — RE-AIMED` and is the C12 mandate in

## VERIFY attempt 1 — what attempt 2 CLOSED (recorded so the finding is not re-filed)

Both of the attempt-1 findings above were u11's own to fix, and both are fixed
in this attempt. Kept here because the *causes* generalise past this unit.

1. **Blank captures — closed.** Root cause confirmed exactly as filed: the
   capture protocol froze the boot sweep instead of only the motion inside it.
   `components/desktop-dressing.ts:revealDesk` clears `<body class="booting">`
   only when every window's ENTRY animation has RESOLVED, and `freezeAt` sets
   `animation-play-state:paused` on `*` — so freezing before the hand-over made
   `shell.css:172` (`body.booting .win{visibility:hidden}`) permanent. Fix, all
   inside `e2e/captures.spec.ts`: wait for the hand-over (`settled()`) BEFORE
   installing the clock and freezing, for the nine shots that are not the sweep;
   `boot-scanline` alone still shoots under `booting`, which is what it frames.
   The three guards were then made able to fail — the shot now asserts `booting`
   is gone, that no mounted `.win` computes `visibility:hidden`, and that the
   framed element itself computes `visibility:visible` and `display != none`
   *before* the element screenshot is attempted. The C15 clipped fallback
   survives, but only for an element that is genuinely painting; it can no
   longer launder a refused shot of a hidden window into a "framing mode".
   Result: 10/10 shots, 0 clipped, five windows painted in every desk shot.
   **Carry past u11:** a capture spec that pauses animations must not pause the
   ones its own reveal logic awaits.

2. **Red-thread flake — closed at the test, and the cause was NOT the thread
   layer.** No `retries`, no `.skip`, no `-g` exclusion (C12/[u11#c7]); [u8#c3]'s
   clipping rule untouched; no production code changed.

   The attempt-1 report guessed "the desk keeps ticking between two reads". That
   is a real hazard and is now handled (see below), but it was **not** what made
   the file red. Instrumenting the failure — report the state that DECIDES a
   missing thread, not just "no thread is drawn" — gave the answer on the first
   loaded run and it was the same every time:

   ```
   no thread is drawn — {"threads":0,"slots":["b-r3-f01",...],
     "driverSlots":{"0":"b-r3-f01"}, "tally":"win win-tally focused", ...}
   ```

   `#w-tally` carries no `hidden` class: **the TALLY is up**, and while it is up
   `planThreads` returns `[]` for every thread by design ([u8#c1], reference
   `app.js:579`). Both anchors were well inside their windows' visible rects and
   a forced redraw still found nothing — the layer was right and the setup was
   wrong.

   Why the setup was wrong is a C17 case in the strict sense. `boot()` drains the
   run, and `drain()` flushes it to its TERMINAL — exactly the phase in which u7
   opens the tally and keeps it open. The file then closed the sheet with its
   `.wc-close` button under a comment that dated itself: *"u7 — the unit that will
   keep the tally shut until the run ends — has not landed, so the suite closes it
   the way the operator does."* u7 has landed. Closing by hand fought the run
   state, so any following frame put the sheet back up and every thread vanished
   at once. Rate: 1 in 5 full-suite runs, ~60 % under a loaded `--repeat-each`,
   and it hit the MID-drag, REPORTS-drag and TALLY-open oracles indiscriminately.

   Re-aimed to the loop's own exit: `#btnNewRun`. The desk lands in a RUN phase
   where the tally is shut *because the run says so*, and with the clock held at
   0 it never reaches the next 21:04. Measured after: the drag describe went from
   9 reds in 15 to **30 green in 30**, and the whole file is green repeatedly.
   Cost: boot waits out the ~9 s count-up before NEW RUN unlocks, so each test in
   the file carries ~10 s; the suite absorbs it in parallel (4.0 min, unchanged).

   Two smaller hardenings ride along, both test-side: `threadSnapshot()` reads a
   path and its anchor rects in ONE page task (one frame by construction, instead
   of two round trips a beat apart), and `holdStill()` = `__feed.rate(0)` stops
   the desk for the geometry oracles — the transport's own pause, not a mock.

   **Carry past u11:** an oracle that reports only *"the thing is not there"*
   costs several runs per diagnosis. Reporting the state that decides it —
   here `tally`, `driverSlots`, both anchor rects and their body rects — turned a
   three-attempt guess into one run. The instrumentation stays in the file.

3. **Two capture shots now seat blocks before freezing (new, u11-owned).**
   `shell-desktop-1280x800` and `red-thread-overlay` reference frames both show
   the thread crossing REPORTS → AGENT FILE; a freshly booted desk has nothing
   slotted, so those two build shots framed a threadless desk. The spec now
   drains, reads the ids the run actually rendered (never fixture content, C3),
   seats the first two through u4's `__agentFile.place()` and redraws — the same
   dev handles `e2e/red-thread.spec.ts` drives. No production code changed.

4. **`e2e/fonts.spec.ts`'s ~1 s budget was measuring the scheduler, not the
   build (re-aimed, C12/C17 — the number is untouched).** `nav.duration` is wall
   clock and the spec runs on the `chromium` project — one of three web servers
   in a suite whose other workers drive browsers on the same box. Same bytes,
   three readings: ~700 ms with the machine to itself, **1168 ms** in a plain
   full-suite run, **1278 ms** with two suites at once. `NAV_BUDGET_MS` stays at
   1000 and the assert stays; it now reads the BEST of five fresh navigations,
   the sample least contaminated by the neighbours. A build that genuinely
   crossed 1 s crosses it in every sample and still fails. Recorded because the
   underlying fact belongs to u10: the finished desk's first render pulls ~1.05 MB
   across 50 slices (already routed in this file), and a payload that size is why
   a 1 s wall-clock budget sits close enough to the edge for machine noise to
   decide it. u11 changed no production code and did not widen the budget.
