## 2. K1 — §8-1's union needs a sixth term, for the player

§8-1 reads "every slot resolves to exactly one of `GateView ∪ BeatView ∪
RoundView ∪ ComposerDeps ∪ PROXY_OWNED_SLOTS`". Run literally over the live
views, that closure leaves **`BLOCKS`** unassigned in spirit: call contracts §6
assigns it to *the player* ("mined from the actual generated text of timeline
and reports"), and it reaches the composer through a construction dependency
(the block store) rather than through any view.

Papering over it by leaning on `COMPOSER_DEP_SLOTS` alone would have hidden the
fact that the composer does not *author* the slot, it only resolves ids the
player picked. So the closure's supplier map carries an explicit sixth term,
`PLAYER_SUPPLIED_SLOTS = ['BLOCKS']`
(`tests/acceptance/fixtures/closure.ts`), and `BLOCKS` being named by both
`PlayerSupplied` and `ComposerDeps` is deliberately **not** counted as a double
supply — the doubling rule is engine-side ∩ proxy-owned, not set ∩ set, because
the property §8-1 protects is "the client cannot rewrite the agent's character".

The same rule is what keeps `TEMPERAMENT` (in `GateView` *and* `RoundView`, by
requirement of §8-6) from reading as a double supply.

**Who resolves it:** whoever next edits contract-engine-composer §8 should add
the player to the union's wording. Nothing in `src/**` changes.

## 4. What the suite drives, and why it is the real pack

Both rigs in `tests/acceptance/fixtures/rig.ts` run over the shipped 우는다리
datapack and the real merged `src/**` slice — schedule builder, state core, beat
driver, id allocator, feed builders, round assembler, composer, block store,
live driver, fixture provider — all imported, none re-implemented. A hand-built
fixture could satisfy every one of §8's criteria while leaving the shipped
scenario broken, and three criteria are only meaningful against real content:
§8-2 needs a beat whose effect moves `trust` (G1's buckets carry ±5…20), §8-8
needs a run that generates lines on every channel, §8-5 needs a real Call 1 →
Call 3 trace of a non-trivial `inner_note`.

Two seams are watched and neither is altered: the transport (requests and
response bodies, passed through untouched) and the `ViewEvent` stream.

`createScriptedEngine` (e7's `tests/driver/engine-fixtures/`) is reused as the
`EnginePort` rather than a second binder being written for this suite. It is
already parameterised by pack, and §8 is about what that port and its
collaborators produce. **Steer candidate**, restating `discovery/e9.md` §1: when
`src/engine/index.ts` `createEngine` lands, both it and
`tools/driver/run/bind.mjs`'s `createEnginePort` collapse into it, and this
fixture should re-point at the product factory.

## A14–A19 are a presence census, not an execution proof (r2 finding, round 2)

`tests/acceptance/gates.test.ts` asserts that each gate command appears as a
string in this file. It does **not** assert the command ran or that it passed —
a prose line mentioning `npm ci` satisfies its check as surely as a recorded
pass would (r2 measured the match counts: 3/1/1/1/2). The file's own docstring
claimed "a green suite cannot hide a gate nobody executed", which is not what
the assertions do. That claim has been withdrawn in the source.

Enforcement moved to where it can shell out. `.github/workflows/ci.yml`'s root
job now runs `npm run build` (A16) and `npm run probe:selftest` (A17) alongside
`npm run check` and the vitest suite; the `proxy` job covers A18. r2's
correction to their own finding, worth keeping: A16 *was* running — in
`deploy.yml`, on push to main only, which is after a merge and therefore too
late to gate one.

**Still enforced by nothing mechanical: A19 (frozen inputs.)** During a
super-pipeline run it is VERIFY's `git diff` guard; outside one it is review.
There is no CI job that fails when a frozen path changes. Closing it means a
workflow step diffing the run's `frozen_globs` against the base — a harness
concern rather than a unit's, which is why this run did not add one.

## The run record has UI consumers, so its raw log needs a filter at the boundary

r2's forward caution, recorded rather than acted on. `reports` in the run record
is the raw Call 3 response copied verbatim by the transport wrapper, so it can
contain `[속내] …` — correct for a diagnostic log, and the player-facing path is
filtered downstream by `withholdInnerNote` before anything is minted or emitted.

But contract-run-artifacts §1 lists **"report viewer · mining UI"** among the
run record's consumers. The first unit that renders a stored record into either
must apply the mint-boundary filter itself; reading `reports` straight onto a
surface a player sees would reintroduce the §8-5 breach this run just closed,
from the archive instead of from the engine.
