## 1. Blocker A1 still stands, and it caps u5's e2e half

`src/client/shell/boot.ts:63` still opens the desk on
`placeholderBootRun(identity)` (`src/client/shell/boot-run.ts:26`), whose stream

```ts
events: [{ type: 'meta', run: RUN, runs_left: RUNS_LEFT, carried: [], archive: [] }],
```

`e2e/live-feed.spec.ts` is deliberately self-relative — it reads its expectations
from `__shell.frame().events` rather than from any fixture literal (C3), so the
purely comparative tests (stream order, verbatim text, marks) will go green
against an empty stream. But the criteria that assert *content exists* cannot:

- `diegetic waiting` — "the phrasing table covers every `waiting.for`" needs
  `waiting` events for all three of judgment / narration / report;
- `fallback line` — the 17:33 `.fl-fallback` with mark `※` and its
  `data-fallback-class`;
- `round renders in order` — the ≤3-symptoms-per-beat cap, and the symptom-free
  beat that must render `(변화 없음)` with `data-empty="1"`;
- `lines land on the clock` — `seek('21:04')` landing "every stream line exactly
  once", and `count()/kinds()/stamps()` agreeing with a non-empty DOM.

**u5 cannot resolve this from inside its file_globs**: `shell/boot.ts` and
`shell/boot-run.ts` belong to u3, and the authored demo run is u2f's, blocked on
`src/shared/segment.ts` (frozen for u5). Integrator: the boot rewire from
`placeholderBootRun` to the authored run has to land before u5's gate can be
honestly green, or u5's e2e will keep passing/failing on an empty stream for
reasons that have nothing to do with u5's code.

## 2. Spec gap — `window.__feed` needs `seek` / `rate`, and the unit spec does not say so

`.claude/super/units/u5/tests.md` § "Notes for BUILD" enumerates the required
exports, and for `run-feed.ts` lists `createRunFeed` with the handle
`{count, kinds, stamps}` (which is exactly what the implemented `RunFeed`
interface exposes, `src/client/components/run-feed.ts:125`).

The e2e spec needs **two more members on `window.__feed`** that appear nowhere in
that list:

- `__feed.seek(at: string)` — `e2e/live-feed.spec.ts:103`
- `__feed.rate(r: 0 | 1 | 4)` — `e2e/live-feed.spec.ts:111`

They are load-bearing: `boot()` waits on `window.__feed` existing, every
`describe` calls `setRate(page, 0)` + `seek(page, '21:04')` in `beforeEach`, and
design D13 makes `seek` the only way to reach 21:04 inside an e2e budget (×1 is
~77 s of real time for the whole day). Both must delegate to the driver clock —
`[u5#c6]` forbids the window owning a timer — so the natural home is the window
file, not `RunFeed`. Worth folding into the unit spec's export list so the next
IMPLEMENT does not rediscover it from a Playwright stack trace.

## 3. Spec/lint friction — `FALLBACK_CLASS` is a required export that cannot be imported

`tests.md` requires `fallback-notice.ts` to export `FALLBACK_CLASS` (the engine
§5 call-number → class table, `[u5#c5](a)`). `run-feed.ts:23` imports it, never
uses it, and the project's `tsc` runs with `noUnusedLocals`, so `npm run check`
— and therefore `npm run build` — fails on TS6133. `npx vite build` alone is
clean, so the two disagree about whether the unit builds.

Not a cross-unit issue (both files are u5's), but flagging the shape: the export
is consumed by the **test**, not by `run-feed.ts`, and the unit spec reads as
though `run-feed.ts` is its consumer.

## 7. Seam friction — `waiting active:false` is due one event *before* its answer

`ViewEvent`s with no stamp of their own inherit the stamp of the last stamped
event (`fixture-driver.ts:49-67`). u2f emits the closing `waiting active:false`
*before* the reply line (`woodari-run03.ts:196`), so both carry the wait's own
minute: at `seek('09:25')` the driver has already released "the wait is over"
while the answer itself (09:26) is still unreleased.

Rendering the seam literally would leave **no open marker at 09:25**, which
`[u5#c4]`'s "an open wait shows one breathing marker" asserts must exist — the
marker is what stands in for the missing answer. u5 therefore treats
`waiting active:false` as *armed*, and takes the marker down when the next feed
line lands. The seam event is still the only thing that ends a wait ([u5#c4]);
only the frame it lands on changes. If the seam ever wants literal semantics,
the fixture should emit the close *after* the reply, or `waiting` should carry
its own clock.

## 8. Reference deviation — the tail is followed by measurement, not by the rAF alone

`app.js:449` (`prefillFeed`) pins the scroll once in a `requestAnimationFrame`.
Ported as-is, `[u5#c7]`'s "the feed follows its tail" fails by ~19 px in real
Chrome: u10's self-hosted webfonts swap in **after** the backlog has landed and
reflow the whole fanfold, and nothing re-pins. `[u5#c6]` forbids a second rAF or
any timer, so the port adds a `ResizeObserver` on `#feedList` that re-pins on a
height change. It observes size and moves the scroll; it lands no line, and the
only clock in the window is still the driver's.

## 10. e2e port 5174 is shared by every parallel worktree — results can be another unit's

`playwright.config.ts` pins `PORT = 5174` with `reuseExistingServer: !CI`. Six
unit worktrees run in parallel off the same port, so a `npx playwright test` run
can silently be served **another worktree's tree**. This is what attempt 1
recorded as "26/26 abort in `boot()`": re-running the identical command against
a dev server started from *this* worktree turned the same 26 green with no code
change in between, and a `curl` of `…/src/client/windows/live-feed.ts` on 5174
afterwards returned the u3 **stub** — i.e. a sibling worktree's file.

**Anyone re-running u5's gate must confirm the server is this worktree's** (start
`npm run dev -- --port 5174 --strictPort` from this directory first, or `curl`
the module path and check it is not the stub). A per-worktree port (or
`webServer.command` with `--port ${PORT}` derived from the worktree) would end
the whole class of ghost failures.
