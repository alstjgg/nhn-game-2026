# e7 — DISCOVERY

The run's first real integration point: e2's state core, e3's beat driver, e4's
feed builders, e5's composer and e6's transport, bound behind one object that
speaks the §5.2 seam. Everything below is either a spec premise that had gone
stale, a decision the docs left open, or a seam friction the next unit inherits.

## Spec assumptions resolved during build

1. **Spec §4's premise ("e0 has not landed") was void.** `src/driver/index.ts`,
   `src/engine/index.ts`, `src/composer/index.ts` and `src/transport/**` were all
   present. Built against the landed names; no e0 file was rewritten.
2. **e6's `TransportResult` landed exactly as §4 assumed** (`{ok:true, body}` /
   `{ok:false, fallback, code, status, requestId, attempts, error}`). No
   adaptation was needed in `ports.ts` — `TransportPort = Transport`, verbatim.
3. **The spec checklist item "`src/engine/index.ts` · `src/composer/index.ts` —
   barrel wiring" is DROPPED.** `tests/scaffold/skeleton.test.ts` (outside e7's
   globs) asserts that `createEngine`, `createComposer` and `createDriver` each
   throw `unimplemented: <symbol>`. Rewiring either barrel makes that suite red.
   e7 therefore edits neither, and `createDriver` stays the throwing stub while
   `createLiveDriver` is **added beside it** (OCP). Whoever ratifies the engine's
   own construction shape gets to retire the stub and move the harness below.

## Decisions taken (the docs are silent on each)

1. **Decision 1 — the driver wraps, never mints.** `engine.feed()` returns this
   beat's lines with ids already minted; the driver keeps a per-beat cursor and
   emits only the tail on each flush. That cursor is what splits a beat into the
   pre-narration flush (script line · utterance `u` · symptoms) and the
   post-narration flush (`n`, `q`). It resets at `beat_start`.
2. **Decision 2 — `meta` is out of scope.** Dependency direction is
   runloop → driver (physical §3.1), so this module cannot import the runloop.
   The stream carries no `meta` event; e8/e9 fold that channel on above e7.
   `new_run` is accepted by `submit` and ends the current run — what happens
   next is the host's.
3. **Decision 3 — `score` is optional.** No document assigns the scoring rule to
   any unit. Absent a `scorer` dep the driver emits no `score`; present, it emits
   `score` immediately before `run_end`.
4. **Decision 7 — `assertSeamClean` is re-implemented at
   `src/driver/seam-guard.ts`.** `src/client/**` is a frozen glob and
   `src/driver/` may not reach into it, so the rule is re-stated rather than
   imported. Two copies now exist (`src/client/driver/seam-guard.ts` is u2's).
   **Consolidating both into `src/shared/` is a later unit's call** — the
   duplication is deliberate and is the cheapest way to keep the import
   direction clean today. Difference worth noting: this copy **returns** the
   event it checked, so the guarded value is the only thing a caller has to
   emit; the client copy returns `void`.

## Ports declared here because no sibling ships them

`src/driver/ports.ts` owns `EnginePort` · `ComposerPort` · `TransportPort` ·
`ScorerPort` · `BlockStore` · `MutableBlockStore` · `OpAck` · `LiveDriverDeps`.

- **`EnginePort extends Engine`** — e0's `Engine` is the four view getters
  (contract §2 + §2.0). e3's beat driver is richer, so the port adds `current` ·
  `submitStance` · `applyBeatEffects` · `applyNarration` · `applyReport` ·
  `advance`. All structural; nothing imports a concrete engine.
- **The three ingest points take `T | null`, and `null` IS the fallback path.**
  Recovery is the **engine's**, never the driver's (spec-engine §5): substituting
  a gate's `default_stance` needs a field `gateView()` deliberately does not
  expose, so the driver could not perform it even if it wanted to. The driver
  branches once, on `result.ok`, and never on a grade.
- **`LiveDriverDeps = DriverDeps & {…}`** — an intersection, so it provably
  extends e0's frozen shape and `skeleton.test.ts`'s `_d1` check stays green.
- **`LiveDriver` adds `slottedIds()`** beyond spec §1's four methods. A10 asserts
  that `slot`/`unslot` "change `slottedIds()` observably" and nothing else on the
  surface exposes slot state.

## Seam friction the next unit inherits

1. **`buildFeed` is all-at-once, but the ratified seam splits the beat around
   Call 2.** Spec decision 1's two flushes cannot be two `buildFeed` calls — the
   second would re-mint `u`. The harness therefore calls `buildFeed` with
   `narration` omitted for the pre-slice, and `classifyNpcLines` +
   `ids.next('n'|'q')` for the post-slice. **A `buildPreFeed`/`buildNarrationFeed`
   split belongs in `src/engine/feed/`, not in `src/driver/`** — a driver that
   re-implements the mint order is exactly the drift D1's golden exists to stop.
2. **Emitted order vs. the D1 golden.** `buildFeed`'s mint order is
   `t* → u → n → q → symptom`, but spec decision 1 puts symptoms in the
   *pre*-narration flush. The **emitted** order is therefore
   `t* → u → symptom → n → q`. Id order is unchanged (the golden still holds);
   only the on-screen position of the symptom rows moves. If §5.2 wants the
   symptom rows after the narration, that is a one-line change in the harness's
   pre-slice — flag it before the client pins a layout to it.
3. **The engine's construction shape is still unratified.** The object binding
   e2+e3+e4 into one `EnginePort` is a **test harness**
   (`tests/driver/engine-fixtures/scripted-engine.ts`), not product code:
   decision 1 forbids shipping it under `src/driver/` (that would put id minting
   inside the driver) and `src/engine/index.ts` is frozen as a stub. Everything
   it calls is the real merged slice — `buildSchedule` · `createBeatDriver` ·
   `initState` · `applyEffects` · `renderSymptoms` · `createIdAllocator` ·
   `buildFeed` · `classifyNpcLines` · `buildReportSentences` ·
   `assembleExperienced`. **Whoever implements `createEngine` should lift that
   glue verbatim**, and the harness should then shrink to a pack + a run number.
4. **The key-level guard cannot catch a *value*-level echo of `inner_note`.**
   The round assembler puts `[속내] <inner_note>` into `EXPERIENCED` (contract §5
   — that is the one place the note is allowed to be read), and Call 3's response
   becomes `report.facts`. A reporter that echoes its `EXPERIENCED` slot back
   verbatim therefore puts the note's *text* on the stream under a perfectly
   legal key. `createFixtureProvider`'s offline reporter does exactly that, so
   the leak suite pins a non-echoing reporter body. **This is a reporter-prompt
   concern (proxy `prompts/reporter/`), not a seam-type one** — no key-level
   guard can or should catch it. Worth one line in the reporter's system layer.

## A14's literal wording does not survive contact with the branch graph

A14 asks that `git diff --name-only main -- tests/driver/` list only
`engine-*.test.ts`. At this base it lists **all five** of u2's seam suites too —
they were added by *this run's* branch and do not exist on `main`, so they are
"added" relative to it regardless of what e7 does. The criterion is enforced by
its intent instead: `tests/driver/engine-boundaries.test.ts` pins the SHA-256 of
each of the five files, which is a strictly stronger check (a byte pin cannot be
satisfied by a plausible-looking edit), plus an assertion that every file e7 did
add is named `engine-*`.

Related: `tests/driver/engine-fixtures/` is not matched by vitest's
`include: ['tests/**/*.test.ts']`, so the harness never runs as a suite. A14's
literal glob excludes that directory; read A14 as "no pre-existing `tests/driver`
file is modified or deleted".

## Small things, recorded so nobody re-derives them

- `deploy` is canonicalised **twice** — de-duplicated and code-unit-sorted by the
  membrane, and again by e5's `resolveBlocks`. The second is the contract's; the
  first makes the driver's own `deployed()` answer order-free, which is what a
  future replay writer will diff.
- `mine` on a symptom line answers `{ok:false, reason:'not_minable'}` because a
  symptom carries no `sentence_id` at all (contract §8-9) — the store never sees
  one, so there is no rule to remember.
- The block store has **two tiers**: `seen` (every emitted feed line + report
  sentence) and `mined` (what `blocks()` returns and what the composer resolves
  against). Deploying an unmined id is therefore impossible by construction, not
  by a check.
- `new_run` submitted mid-`step()` is honoured at that step's **end**, so a round
  is never severed between its last `beat_end` and its `report`.
