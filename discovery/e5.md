# e5 — discovery

## 1. The block store outruns e0's `ComposerDeps` (spec decision 2 / design D2)

`contract-engine-composer.md` §3 says the composer "resolves ids to text through
the block store the driver passes in", but the `ComposerDeps` literal in the same
section lists only `reportGuidance` — and e0's landed
`src/composer/index.ts` transcribes that literal exactly
(`ComposerDeps = { reportGuidance: unknown }`). The views are the engine's and are
frozen by §2, so the store cannot travel in a view either.

**Default taken:** `createComposer` accepts
`ComposerDeps & { reportGuidance: ReportGuidance; blocks: BlockStore }`
(exported as `ComposerRuntimeDeps` from `src/composer/compose.ts`). One
intersection closes both gaps: it *adds* the store and *narrows* e0's `unknown`
to e1's canonical `ReportGuidance` without redeclaring that type
(`unknown & ReportGuidance` ≡ `ReportGuidance`). Reversible — if the contract is
amended to put the store in `ComposerDeps`, drop the intersection and nothing
else moves. The unit that rewires the barrel (e7) is the natural place to
reconcile.

## 2. Spec S1 was wrong about where the views live — corrected

Spec S1 assumed `GateView`/`BeatView`/`RoundView` could be imported from
`./index.ts`. e0's barrel *imports* them from `../engine/index.ts` and does not
re-export them, so this unit imports the views from `../engine/index.ts` and only
`Composer`/`ComposerDeps` from `./index.ts`. Both are `import type` — a value
import of `../engine/` is banned by A18, and the test's source scan strips
`import type` lines precisely so the type edge stays legal.

## 3. An unresolved block id throws (spec decision 5 / design D5)

`resolveBlocks` de-duplicates, sorts, then resolves every id **before** any
`CallRequest` is constructed; the first miss throws
`Error("unknown block id: <id>")` and nothing partial escapes. Rationale: the
engine mints the ids and the driver owns the store, so a miss is a bug in the
run, not a player action — and skip-and-continue would corrupt a C-BLOCK
comparison invisibly (two runs with "the same" block set composing different
bytes). Reversible by a reviewer who prefers skip-and-continue; recorded as a
default, not a ratified decision.

## 4. S8's fallback was not needed (design D8, re-measured here)

`tests/composer/proxy-bridge.ts` imports `proxy/src/{calls,prompt,default-prompt,
types,prompt-bundle.generated}.js` with plain relative specifiers. Root
`moduleResolution: "bundler"` maps `.js` → the `.ts` source, those five pull in
only `errors.ts` (no `@aws-sdk`, which `handler.ts` would drag in), and both
`npm run typecheck:test` and `npx vitest run` are green on it. No
`unknown`-narrowing and no tsconfig change (every tsconfig is frozen).
`parseCallRequest` is unexported and lives in the `@aws-sdk`-importing
`handler.ts`, so A6 **transcribes** its four checks in `assertEnvelope` with the
real `isCallType` imported; the source-line citation in that file is the drift
guard.

## 5. Sort is `Array#sort`, never `localeCompare`

Canonical block order is `[...new Set(ids)].sort()` — UTF-16 code-unit order,
locale- and ICU-independent, identical in Node and the browser. `localeCompare`
would put the fixtures' Hangul id in a different place depending on the host's
ICU data, which is exactly the drift that breaks "same block set ⇒ same bytes".
`tests/composer/compose.test.ts` A10b asserts the two orders differ for the
fixture set, so a future "make it read nicer" swap fails loudly.

## 6. Frozen paths

This unit wrote nothing under `proxy/**`, `tools/lib/{compose,calls}.mjs`, or
`src/composer/index.ts`, and touched no tsconfig. A20's git half is asserted
inside the suite; `cd proxy && npm ci && npm test` is green (39 tests, 3 files),
so D3 prompt byte-parity is unbroken.
