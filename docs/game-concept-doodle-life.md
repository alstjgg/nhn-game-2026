## 1. 개요

**한 줄 피치:** AI가 만든 정원의 주민들이 말과 몸짓으로 저마다의 문제를 흘린다.
플레이어는 숨은 필요를 추리해 해결책이 될 생명체를 그리고, VLM이 읽어 낸 자신의
그림이 실제 정원에서 살아 움직이며 부탁을 해결한다.

| 항목 | 내용 |
|---|---|
| 장르 | 코지 캐릭터 창작 + 관찰·추론 퍼즐 |
| 플랫폼 | 웹, PC 브라우저 우선. 마우스·트랙패드·펜 입력 |
| 세션 구조 | 주민 부탁 1개 = 약 2–4분. 3–5분 플레이에 관찰 → 그림 → 판독 → 결과 장면 1회 완결 |
| 타겟 | 코지 퍼즐 이용자, 낙서를 좋아하지만 그림 실력에는 자신 없는 사람, 생성형 AI의 해석을 놀이로 즐기고 싶은 사람 |
| 레퍼런스 | Drawn to Life·Chicory의 “그림이 세계가 되는 감각” / Is This Seat Taken?의 “행동에서 숨은 요구를 읽는 퍼즐” / Scribblenauts의 복수 해법 |

플레이어는 정답 능력을 메뉴에서 고르거나 LLM에 자유 텍스트로 선언하지 않는다. 주민의
문제를 관찰하고 **그림으로 답한다.** 정답은 “새”나 “비행기” 같은 특정 사물이 아니라,
높은 곳에 닿기·소리를 모으기·무언가를 잇기처럼 문제를 해결하는 **눈에 보이는 기능**이다.
같은 부탁에도 서로 다른 형태의 그림이 정답이 될 수 있다.

## 2. 첫 60초 — 심사위원이 보게 될 장면

아래 장면은 정원 생성을 미리 끝내고 소소의 부탁을 바로 보여 주는 **튜토리얼
패스트 패스**다. 일반 라운드는 관찰과 자유로운 그리기를 포함해 2–4분이지만, 첫
시연에서는 핵심 페이오프를 60초 안에 한 번 관통한다.

종이 질감의 작은 바람 정원이 펼쳐진다. 길고 납작한 몸을 접고 다니는 **소소**, 세
갈래 다리로 화분 사이를 건너는 주민, 가운데가 뚫린 고리 모양 주민이 각자 다른
움직임으로 생활한다. 화면 어디에도 둥근 기본 몸체를 공유하는 캐릭터는 없다.

높이 매달린 **리본 풍경**이 세 번 울린다. 풍경을 보던 소소가 몸을 길게 뻗지만 닿지
못한다. 건너편의 작은 종은 두 번만 울린다. 소소는 자기 옆자리를 비운 채 마지막 소리를
기다리다가 말한다.

> “높은 리본 풍경이 세 번 울면, 건너편 작은 종은 늘 마지막 소리를 놓쳐.”

화면 한쪽에 이번 관찰의 초점이 나타난다.

> **소소의 부탁:** 높은 곳과 건너편 사이에서 끊기는 바람 소리를 이어 줄 생명

[그림으로 답하기]를 누르면 같은 화면 위에 캔버스가 열린다. 소소의 말, 리본을 향해
뻗던 행동과 두 번만 울린 종을 언제든 다시 볼 수 있다. 플레이어는 몸 양옆에 넓은
막을, 머리에는 오목한 귀 두 개를, 꼬리에는 속이 빈 고리 무늬를 그린다. 삐뚤하지만
의도는 분명하다. [태어나기].

그림의 넓은 막에 빛이 번진다.

> “몸 양옆의 넓고 얇은 면 — 바람을 오래 받는 막으로 읽었습니다.”

두 귀에도 작은 파문이 생긴다.

> “안쪽으로 모인 한 쌍의 형태 — 멀리서 온 소리를 모으는 귀로 읽었습니다.”

꼬리의 고리 무늬에도 파문이 차례로 번진다.

> “속이 빈 고리가 이어진 꼬리 — 받은 울림을 되돌려 보내는 통로로 읽었습니다.”

그림은 둥근 프레임 속 마스코트로 바뀌지 않는다. 플레이어가 그린 실루엣 그대로
캔버스에서 빠져나와 바람을 타고 리본 풍경까지 올라간다. 귀로 세 번째 울림을 받고,
고리 꼬리로 건너편 종에 전한다. 작은 종이 세 번째 소리까지 답하자 소소가 비워 둔
자리를 내어 준다.

오른쪽에 관계 기록이 들어온다. **「소소가 기다리던 마지막 박자」**.

이 60초에 게임의 전부가 있다:
**부탁을 읽는다 → 해결책을 상상해 그린다 → 그림이 읽힌다 → 살아서 해결한다 → 관계가 남는다.**

## 3. 경험 목표

| 키워드 | 플레이어가 느끼는 것 |
|---|---|
| **읽어 냈다는 손맛** | 대사, 시선과 환경 흔적을 조합해 주민이 정말 필요한 것을 알아낸 순간 |
| **답을 발명하는 창작감** | 준비된 선택지에서 고른 것이 아니라 내 형태로 해결 방법을 만들었다는 감각 |
| **내 그림이 읽혔다는 납득** | AI가 결과만 말하지 않고 판단의 근거가 된 선과 면을 정확히 짚어 주는 순간 |
| **살아났다는 놀라움** | 원본 낙서의 실루엣과 색이 그대로 몸이 되어 의도한 기능을 수행하는 장면 |
| **부드러운 실패** | 완벽히 풀지 못해도 그림의 실제 특성에 맞는 사건과 다음 시도를 위한 단서가 남는 경험 |
| **다음 부탁의 기대** | 주민들의 다른 문제를 보면 새로운 생명체의 모습이 머릿속에 먼저 떠오르는 상태 |

## 4. 핵심 루프 (주민 부탁 1개 ≈ 2–4분)

```text
정원 생성 — NPC · 관계 · 공간 · 잠긴 주민 부탁이 만들어진다
  → 부탁 선택 — 주민 한 명의 문제에 집중한다
  → 관찰·추론 — 짧은 대사 + 몸짓 + 환경 흔적을 읽는다
  → 그림으로 답하기 — 필요한 기능을 형태로 표현한다
  → VLM 판독 — 가시적 근거 + 열린 특성 + 내부 기능 태그
  → 로컬 판정 — 그림 전에 잠긴 부탁과 기능 태그를 비교한다
  → 생명화된 결과 — 그림이 직접 움직이고 NPC들이 반응한다
  → 정원 변화 · 관계 기록 · 생명체 도감
  → 새 생명체가 정원 주민이 된다 → 다음 부탁
```

- **부탁이 그림보다 먼저다.** 플레이어는 그릴 이유와 관찰할 문제를 가진 뒤 캔버스를 연다.
- **그림 자체가 답이다.** 판독 후 행동 카드나 대상 메뉴를 다시 고르지 않는다.
- **한 라운드, 한 부탁이다.** 주변 주민은 장면에 반응하지만 동시에 별도의 정답을 요구하지 않는다.
- **정답 형태는 여러 개다.** 날기, 뜨기, 늘어나기처럼 목적을 달성하는 서로 다른 기능을 허용한다.
- **틀림은 새 정보다.** 부분 해결은 빠진 조건을 보여 주고, 뜻밖의 결과도 고유한 관계 기록으로 남는다.
- **첫 페이오프를 보장한다.** 제출한 그림은 결과 등급과 무관하게 살아 움직이는 장면을 반드시 만든다.

## 5. 핵심 시스템

### 5.1 정원과 주민

정원은 세션 시작 시 한 번 생성된다. 테마, 공간, 소품과 함께 서로 다른 외형·성격·관계를
가진 주민 3명이 등장한다. 각 주민은 해결되지 않은 부탁 하나와 그 문제를 보여 주는 반복
행동을 가진다. 플레이어는 정원에서 한 주민을 골라 해당 라운드를 시작한다.

NPC 생성에는 **실루엣 문법**을 둔다.

- 같은 정원에서 실루엣 계열, 가로세로 비율과 지지 방식을 중복하지 않는다.
- 긴 몸, 갈라진 몸, 가운데가 빈 몸, 다족형, 부유형, 겹판형처럼 무게 중심이 다른 형태를 섞는다.
- 눈과 입의 위치만 바꾼 둥근 조약돌 캐릭터를 서로 다른 주민으로 취급하지 않는다.
- 성격은 대사뿐 아니라 걷는 방식, 쉬는 자세와 소품을 다루는 버릇으로 드러낸다.

### 5.2 주민 부탁과 Quest Contract

주민의 문제와 허용할 해법은 플레이어가 그림을 보기 전에 `QuestContract`로 만들고
잠근다. LLM은 제출된 그림을 본 뒤 문제나 정답 범위를 바꿀 수 없다.

```ts
interface NeedRule {
  // 안쪽 배열은 OR, 바깥 배열은 AND
  allOf: string[][]
}

interface QuestContract {
  questId: string
  ownerNpcId: string
  problemState: string
  primaryPurpose: string
  primarySolutions: NeedRule[]
  bonusPurpose?: string
  bonusSolutions?: NeedRule[]
  partialAffordances: string[]
  unexpectedEffectByAffordance: Record<string, EngineEffect[]>
  clues: {
    dialogue: string[]
    behavior: string[]
    environment: string[]
  }
  outcomes: {
    full: EngineEffect[]
    success: EngineEffect[]
    partial: EngineEffect[]
    fallbackUnexpected: EngineEffect[]
  }
}
```

한 부탁에는 반드시 해결해야 할 **주요 필요 하나**와, 깊이를 더할 때만 쓰는
**보너스 필요 하나**를 둔다. `NeedRule.allOf`의 각 안쪽 배열은 “이 중 하나”인 OR,
바깥 배열은 “모두 충족”인 AND다. 여러 `primarySolutions` 중 하나만 완성하면 주요
필요를 해결한다. `glide`, `float`, `stretch`, `listen`, `echo` 같은 값은 엔진이
비교하는 작은 내부 기능 언어이며 플레이어에게 고정 특성 카드로 노출하지 않는다.

소소의 부탁은 다음처럼 잠긴다.

- 문제: 높은 리본 풍경과 건너편 종 사이에서 세 번째 소리가 끊긴다.
- 주요 필요: 소리의 근원에 접근하고, 받은 신호를 건너편으로 전한다.
- 주요 해법 규칙: `(활공 OR 부유 OR 늘어나기 OR 벽 타기) AND
  (울림 OR 소리 운반 OR 신호 보내기)`.
- 보너스 필요: 소소와 같은 박자에 귀 기울인다.
- 보너스 기능 예: 듣기, 박자 맞추기, 함께 기다리기.
- 해법 형태 예: 막 날개 + 큰 귀 + 공명 꼬리 / 풍선 몸 + 소리 깔때기 /
  긴 몸 + 울림을 옮기는 고리.

### 5.3 단서 계약 — 최우선 디자인 검증 타깃

좋은 부탁은 정답을 말하지 않지만 무엇을 추리해야 하는지는 알 수 있다. 모든
`QuestContract`는 같은 진실을 가리키는 독립 단서를 두 채널 이상 제공한다.

1. **대사:** 문제의 결과나 반복되는 현상을 1–2줄로 말한다.
2. **행동:** 시선, 거리 두기, 손짓과 반복 몸짓으로 같은 문제를 가리킨다.
3. **환경:** 닿지 않는 소품, 끊긴 흔적이나 비어 있는 자리로 문제가 실제로 보인다.
4. **비모순:** 감성적인 비유도 잠긴 문제 상태와 어긋나면 사용하지 않는다.
5. **비노출:** 정답 기능의 이름이나 정답 사물의 형태를 그대로 명령하지 않는다.
6. **정보량 제한:** 행동·대상·타이밍을 한꺼번에 모두 숨기지 않는다. 대상이나 반복
   타이밍 중 하나는 UI와 환경에서 명확히 보여 주고, 해결 기능을 추리하게 한다.

**너무 모호함**

> 바람이 빈자리를 기억하고 있어.

무엇이 문제이고 어디를 관찰해야 하는지 알 수 없다.

**너무 직접적임**

> 날개와 큰 귀가 있는 새를 그려 높은 리본까지 날아가 줘.

해결 형태와 기능을 모두 말해 그림 퍼즐이 사라진다.

**목표 톤**

> 높은 리본 풍경이 세 번 울면, 건너편 작은 종은 늘 마지막 소리를 놓쳐.

대사만으로 정답 형태는 알 수 없지만, 높은 풍경을 보는 시선과 닿지 못하는 몸짓, 두
번만 울리는 종을 함께 보면 필요한 기능을 추리할 수 있다.

### 5.4 캔버스

주민 부탁 화면 위에 겹쳐 열리는 단순한 캔버스다. 붓 굵기, 색 팔레트, 지우개,
되돌리기와 전체 지우기만 둔다. 정답을 텍스트로 입력하거나 능력을 직접 선택하는 UI는 없다.

- 주민의 대사와 발견한 환경 흔적을 그리는 동안 계속 다시 볼 수 있다.
- 하드 타이머는 두지 않고, 짧게 그려도 충분하다는 소프트 안내만 제공한다.
- 제출 전 원본 그림이 캐릭터의 실제 몸이 된다는 사실을 명확히 알린다.
- 선의 매끄러움, 채색 완성도와 그림 실력은 능력의 강함에 영향을 주지 않는다.

### 5.5 VLM 그림 판독 — 최우선 기술 빌드 타깃

VLM은 현재 부탁의 정답 태그를 받지 않고 그림만 독립적으로 읽는다. 정답을 알고
날개가 아닌 형태를 날개라고 끼워 맞추는 것을 막기 위해서다.

판독 결과에는 다음이 포함된다.

- 이름과 한 줄 본질
- 그림에서 실제로 보이는 특성 2–4개
- 특성마다 근거가 된 선·면·색·배치 영역
- 판정용 내부 기능 태그
- 원본 형태를 움직이기 위한 관절점과 모션 힌트
- 확신할 수 없는 영역과 그 이유

화면에는 자연어 특성과 함께 근거 영역을 직접 밝힌다.

```text
몸 양옆의 넓고 얇은 면
  → 바람을 오래 받는 막
  → “바람을 오래 타요.”

머리 위로 열린 오목한 한 쌍
  → 멀리서 온 소리를 모으는 귀
  → “먼 소리에 귀 기울여요.”
```

플레이어 화면에는 위의 자연어 해석과 근거만 보인다. 엔진은 같은 결과를 내부 기능
태그로 정규화해 판정하지만 태그 문자열 자체는 UI에 노출하지 않는다.

친절함, 용기처럼 그림에서 확인할 수 없는 내면을 성공 조건으로 단정하지 않는다.
판독이 애매하면 능력을 발명하지 않고 “잘 모르겠는 부분”으로 표시한다. 플레이어는
근거를 본 뒤 덧그려 **최대 한 번** 다시 판독할 수 있지만, 자유 텍스트로 원하는
능력을 선언할 수는 없다.

### 5.6 판정과 네 가지 결과

로컬 판정기가 VLM의 내부 기능 태그와 잠긴 `QuestContract`를 비교한다. LLM은 성공과
실패를 결정하거나 결과 등급을 바꾸지 않는다.

| 결과 | 조건 | 플레이 경험 |
|---|---|---|
| 완전 해결 | 주요 필요 + 보너스 필요 충족 | 문제 해결과 추가 관계 장면, 가장 큰 정원 변화 |
| 해결 | 주요 필요 충족 | 부탁을 끝내고 관계 기록 획득 |
| 부분 해결 | 문제에 영향을 주지만 주요 필요의 일부가 부족 | 빠진 조건이 행동과 환경으로 더 분명해짐 |
| 뜻밖의 결과 | 부탁 해결은 아니지만 실제 그림 특성이 다른 사건을 만듦 | 별도 관계 기록을 얻고 부탁은 다시 시도 가능 |

판정식은 고정돼 있다.

- 여러 `primarySolutions` 중 하나의 모든 AND 그룹을 만족하면 **해결**이다.
- 주요 필요와 `bonusSolutions` 중 하나를 함께 만족하면 **완전 해결**이다.
- 완성된 주요 해법은 없지만 그 해법의 AND 그룹 하나 이상 또는
  `partialAffordances`가 맞으면 **부분 해결**이다.
- 위 조건은 없지만 그림의 기능이 `unexpectedEffectByAffordance`에 존재하면 해당
  **뜻밖의 결과**를 실행한다.
- 어떤 기능도 매핑되지 않으면 정원에 태어나는 기본 뜻밖의 장면을 실행한다.

부분 해결이나 뜻밖의 결과로 태어난 생명체도 정원에 남길 수 있다. 플레이어는 그
그림에 덧그려 같은 부탁을 다시 시도하거나, 생명체를 보존하고 새로운 그림으로 도전한다.

### 5.7 원본 실루엣 생명화

모든 플레이어 캐릭터를 공통 원형 프레임이나 블롭 몸체 안에 넣지 않는다. 원본의
외곽선, 색, 빈 공간과 돌출부가 그대로 캐릭터의 몸이 된다.

게임은 그림 뒤에 보이지 않는 움직임 정보만 붙인다.

- 넓고 얇은 면은 굽힘과 펄럭임을 가진다.
- 긴 연결부는 관성 지연과 휘어짐을 가진다.
- 여러 지지점은 번갈아 땅을 딛는다.
- 닫힌 고리는 굴러가고, 열린 고리는 주변 물체를 감싼다.
- 떠 있는 형태는 위아래 호흡과 느린 회전을 가진다.

하나의 블롭 모션을 모든 그림에 적용하지 않고, VLM의 부위 판독과 내부 기능에 따라
메시 변형·관절·이동 방식을 조합한다. 애니메이션이 그림을 예쁘게 다시 그리는 것이
아니라 **플레이어가 그린 형태의 가능성을 드러내는 것**이 목표다.

### 5.8 열린 NPC 반응과 Resolver

판정 직후 LLM은 잠긴 문제, 확정된 결과, NPC 성격과 새 생명체의 공개 특성을 받아
대사·감정·시선·이동과 일시적인 소품 모션을 만든다. 영속적인 정원 변화는
`QuestContract.outcomes`가 이미 정하며, LLM은 그 효과를 표현하는 허용 명령만 고른다.
사건 내용은 매번 달라지지만 결과의 진실은 바뀌지 않는다.

```text
Quest Contract + VLM 판독 + 확정 결과
        ├─ 부탁 주인 Agent → 핵심 대사와 행동
        └─ 관련 주민 Agent → 관계에 따른 짧은 관찰 반응
                         ↓
                  로컬 Resolver
                         ↓
                  하나의 결과 장면
```

기본은 부탁 주인과 관련 주민 한 명이다. 주변 모든 NPC가 별도의 퍼즐을 만들지는 않는다.
`Resolver`는 존재하는 인물과 소품인지, 위치가 충돌하지 않는지, 명령이 엔진에서 실행
가능한지, 선택한 명령이 확정 결과에 허용됐는지 검사한다. 생성이 실패해도 확정 판정과
정원 변화는 안전한 기본 연출로 끝까지 재생한다.

### 5.9 관계 기록과 정원 진행

해결 결과는 점수표보다 세계의 변화로 남는다.

- 플레이어가 만든 생명체 도감
- 주민과 생명체 사이의 관계 기록
- 부탁이 해결되며 달라진 소품·소리·빛과 이동 경로

새 생명체는 다음 라운드부터 관찰자나 관계 대상이 될 수 있다. 이전 생명체가 장면에
참여하더라도 새 부탁을 자동으로 해결하지는 않는다. 매 부탁마다 새로운 그림을 상상할
동기를 유지한다.

## 6. AI 활용

런타임 AI는 세 단계에서만 작동한다.

| 단계 | 역할 | 시점 | 출력 |
|---|---|---|---|
| ① World & Locked Quests | 정원·NPC·관계·부탁 후보 생성 | 세션 입장 시 1회 | 월드 데이터와 검증을 통과한 Quest Contract |
| ② Doodle Reading | 낙서의 가시적 특징 판독 | 최초 제출 1회 + 선택적 재판독 최대 1회 | 근거 영역, 열린 특성, 기능 태그, 모션 힌트 |
| ③ Encounter Reactions | 확정 결과를 NPC별로 연기 | 판정 직후, 관련 NPC만 병렬 | 대사, 감정, 이동과 일시적 소품 모션 명령 |

### 권한 원칙 — 열린 콘텐츠, 닫힌 프로토콜

| 영역 | AI가 생성하는 것 | 규칙·엔진이 지키는 것 |
|---|---|---|
| 월드 | 정원 테마, NPC 외형·성격·관계 | NPC 수, 공간·소품 목록, 실루엣 다양성 |
| 부탁 | 문제 소재, 복수 해법 후보, 감성적 표현 | Quest Contract 스키마, 풀이 존재, 필요 개수 |
| 단서 | 대사, 몸짓과 환경 연출 | 채널 이중화, 정답 직접 노출·모순 금지 |
| 그림 | 이름, 열린 특성 설명과 모션 힌트 | 가시적 근거, 내부 기능 태그, 불확실성 표시 |
| 판정 | 맡지 않음 | 잠긴 부탁과 기능 태그의 결정론 비교 |
| 반응 | NPC별 대사, 감정, 일시적 모션과 장면 구성 | 결과 등급, 영속 상태 변화, 유효한 참조와 허용 명령 |

AI가 정해진 문법 안에서 `QuestContract` 후보를 만들고, 로컬 검증기가 실행 가능한
문제만 사용한다. 표현과 해법의 형태는 열어 두되 퍼즐의 진실과 게임 실행은 닫힌
프로토콜이 지킨다.

### 공정성·가드레일 설계

- **문제 선행 잠금:** 플레이어 그림을 받기 전에 부탁과 허용 해법을 고정한다.
- **정답을 모르는 판독:** VLM에는 선택한 부탁의 정답 기능을 전달하지 않는다.
- **가시적 근거 필수:** 근거 영역이 없거나 그림 밖을 가리키는 특성은 판정에 사용하지 않는다.
- **판정은 AI 밖에 있다:** 성공 등급과 상태 변화는 로컬 규칙이 계산한다.
- **참조 검증:** 존재하지 않는 NPC·소품·행동 명령과 확정 결과에 허용되지 않은 명령은
  `Resolver`가 거부한다.
- **가치 판단 금지:** 미술 실력, 선악, 지능과 외모 평가는 기능 판독에서 제외한다.
- **끝나는 폴백:** 모델 호출이 실패해도 기본 대사와 연출로 라운드는 반드시 끝난다.

### 비용·지연 설계

- 월드와 잠긴 부탁은 세션 동안 캐시하고 플레이어 그림을 본 뒤 다시 생성하지 않는다.
- VLM 판독은 최초 제출 1콜, 플레이어가 덧그릴 때 선택적 재판독 최대 1콜로 제한한다.
- 부탁 주인과 관련 주민 반응은 서로의 장문 사고를 공유하지 않고 병렬 실행한다.
- 별도의 Director → Critic 직렬 체인을 두지 않는다.
- 판정이 끝나면 엔진이 기본 생명화 모션을 즉시 시작하고, 생성 반응을 이어 붙인다.
- 단서 재확인, 화면 이동, 그림 확대, 결과 애니메이션의 각 동작과 기록 열람에는 호출이 없다.
- 모든 키와 모델 호출은 서버 프록시에서 관리하며 클라이언트와 로그에 비밀 값을 남기지 않는다.

## 7. 차별화 — 세 가지

1. **주민의 부탁이 낙서의 동기가 된다.** 빈 캔버스 앞에서 “아무거나 그리세요”라고
   요구하지 않는다. 먼저 읽을 수 있는 문제가 있고, 플레이어는 자신의 가설을 그림으로
   표현한다. 창작과 퍼즐이 한 행동으로 합쳐진다.
2. **선택지가 아니라 직접 그린 형태가 복수 해법의 답이다.** 날개, 풍선 몸, 긴 팔다리처럼
   서로 전혀 다른 이미지가 같은 목적을 달성할 수 있다. 정답 단어를 맞히는 퀴즈가 아니라
   기능을 시각적으로 발명하는 퍼즐이다.
3. **AI의 해석이 근거와 움직임으로 증명된다.** 모델이 “활공 가능”이라고 말하는 데서
   끝나지 않는다. 그렇게 읽은 면을 밝히고, 원본 실루엣이 실제로 바람을 타는 장면까지
   이어진다. 판독·생명화·퍼즐 결과가 하나의 페이오프를 만든다.

정직한 한계: 게임의 품질은 모델 이름보다 단서의 가독성, 근거 판독의 신뢰도와 임의
형태를 살리는 모션 공예에 달려 있다. 셋 중 하나라도 무너지면 그림은 장식이나 주사위로
느껴진다.

## 8. 아트 & 화면

**톤 방향: 종이 위에서 자라는 작은 정원.** 배경은 옅은 종이 결, 색연필과 수채 번짐을
사용한다. 생성 NPC는 정돈된 종이 인형 질감, 플레이어 생명체는 원본의 거친 선과 채색을
그대로 유지한다. 두 질감의 차이가 “이 캐릭터는 내가 그렸다”는 사실을 매 순간 보여 준다.

NPC는 귀여움을 둥근 몸통 하나에 의존하지 않는다. 긴 비율, 비대칭, 빈 공간, 여러 지지점,
겹친 판과 떠 있는 부품을 적극적으로 사용한다. 얼굴은 실루엣을 가리지 않는 작은 신호이며,
캐릭터 구분은 눈·입보다 몸의 구조와 이동 방식이 맡는다.

원본 낙서를 원형 초상 프레임에 가두지 않는다. 카드와 도감에서도 그림의 바깥 여백을
투명하게 두고 실루엣 전체를 보여 준다.

화면 구성:

```text
┌──────────────────────────────────────────────────────────┐
│  바람 정원                                      부탁 1/3 │
│                                                          │
│    [높은 리본 풍경]                                      │
│           〰〰       소소 → 몸을 뻗지만 닿지 못함         │
│                                 [건너편 작은 종: ♪ ♪ ·]  │
│                                                          │
│  ┌────────────────────────────────────────────────────┐  │
│  │ “높은 리본 풍경이 세 번 울면, 건너편 작은 종은     │  │
│  │  늘 마지막 소리를 놓쳐.”                          │  │
│  │  관찰: 높은 곳 · 끊긴 소리                        │  │
│  └────────────────────────────────────────────────────┘  │
│                                                          │
│  [다른 주민 보기]       [그림으로 답하기 ✏]             │
└──────────────────────────────────────────────────────────┘
```

캔버스는 정원을 완전히 가리지 않고 옆에 열린다.

```text
┌──────────────────── 부탁 단서 ────────────────────┐
│ 대사 · 몸짓 · 환경 흔적                           │
├───────────────────────┬───────────────────────────┤
│                       │  색  굵기  지우개  되돌리기│
│   원본 그림 캔버스    │                           │
│                       │  “이 모습 그대로          │
│                       │   정원에 태어납니다.”      │
│                       │          [태어나기]        │
└───────────────────────┴───────────────────────────┘
```

머니샷은 판독 카드가 아니라 **근거가 빛난 원본 그림이 캔버스 밖으로 빠져나와 주민의
부탁을 해결하는 연속 장면**이다.

## 9. 스코프 & 3주 마일스톤 (제안)

**수직 슬라이스 (Must):**

- 정원 1곳, 서로 다른 실루엣의 생성 NPC 3명
- 그림 전에 잠기는 주민 부탁 3개와 플레이 가능한 완주 라운드 1개
- 대사 + 행동 또는 환경의 이중 단서
- 캔버스, 실제 VLM 판독과 근거 하이라이트
- 선택적인 덧그리기·재판독 1회
- 로컬 판정과 네 가지 결과 등급
- 원본 실루엣 기반 생명화
- 부탁 주인 + 관련 주민 1명의 병렬 반응
- 정원 변화와 관계 기록 1개
- 각 모델 단계의 캐시·타임아웃·기본 폴백

**확장 (Nice):**

- 주민 부탁 3개 전체 완주
- 이전 생명체가 다음 장면에 참여하는 관계 반응
- 정원 테마 2–3종과 시간·날씨 변화
- 생명체 도감과 관계 기록 탐색
- 기능 조합이 다른 추가 결과 모션

| 주차 | 목표 |
|---|---|
| 1주차 | 핵심 판정 레일 — Quest Contract·단서 UI → 캔버스 → 실제 VLM 근거 판독 → 로컬 결과. 해석과 단서 품질 우선 |
| 2주차 | 생명화와 상호작용 — 월드·NPC 생성, 원본 실루엣 모션, 부탁 주인·관찰자 반응, 결과 장면 1개 완주 |
| 3주차 | 기능 동결 — 복수 해법·부분 해결 테스트, 지연·폴백 튜닝, 아트·사운드 폴리시, 영상·기술 문서 |

기술 노트: 웹 네이티브(Vite + TypeScript) 기반. 캔버스는 브라우저 Canvas API,
`QuestContract`와 내부 기능 태그는 데이터 스키마로 관리한다. VLM·LLM은 서버 프록시를
경유하고 클라이언트는 구조화된 게임 데이터만 받는다.

| 리스크 | 대응 |

## 부록 A — 검증 근거

### 검증 격차

이 컨셉의 성립 여부는 기능 개수보다 다음 장면들이 실제 플레이에서 이어지는지에 달려
있다. 수치형 품질 점수표를 두지 않고 플레이 화면, 모델 출력과 플레이어의 다음 행동을
직접 확인한다.

1. **부탁이 그림 동기가 되는가 (P0).** 캔버스를 열기 전에 플레이어가 주민의 문제와
   자신이 그리고 싶은 해결 방향을 설명할 수 있는가?
2. **단서가 해독 가능하지만 답을 말하지 않는가 (P0).** 플레이어가 문제는 이해하면서도
   새·날개 같은 한 가지 사물만 강요받지 않는가?
3. **VLM이 가시적 의도를 읽는가 (P0).** 근거 하이라이트를 보고 플레이어가 “왜 이
   기능이 됐는지” 납득하는가?
4. **그림이 퍼즐 답으로 느껴지는가 (P0).** 결과가 메뉴 선택이나 모델의 호의가 아니라
   자신이 그린 형태 덕분이라고 느끼는가?
5. **원본 실루엣이 살아 있는가 (P0).** 서로 다른 임의 형태가 공통 블롭으로 수렴하지
   않고 각자의 무게와 이동 방식을 가지는가?
6. **복수 해법이 실제로 작동하는가 (P1).** 같은 부탁에 날개, 부유 몸, 긴 몸처럼 다른
   그림이 각자의 근거로 해결되는가?
7. **부분 해결이 다음 시도를 돕는가 (P1).** 결과를 본 뒤 무엇을 덧그리거나 다르게
   그릴지 자연스럽게 떠오르는가?
8. **열린 반응이 구체적인가 (P1).** NPC 대사와 행동이 해당 그림·관계에만 맞는 장면처럼
   느껴지면서 잠긴 퍼즐 진실을 해치지 않는가?
9. **대기 뒤 플레이가 이어지는가 (P1).** 생성이 끝난 뒤 결과 장면이 추가 호출 없이
   끊기지 않고 완결되는가?

### 보류한 설계

행동 카드·대상 메뉴를 정답으로 고르는 퍼즐 · 그림을 본 뒤 문제를 사후 생성하는 구조 ·
한 그림으로 여러 주민의 독립 부탁을 동시에 해결하는 구조 · NPC와의 자유 텍스트 채팅 ·
매 클릭마다 이어지는 LLM 시뮬레이션 · Director → Critic 직렬 체인 · LLM의 성공 판정 ·
무한 장기 기억 · 첫 결과 뒤의 무한 후속 행동.

수직 슬라이스는 `부탁 관찰 → 그림 → VLM 판독 → 원본 실루엣의 해결 장면 → 관계 기록`
한 사이클을 완성하는 데 집중한다.

## 부록 B — 용어집

- **Quest Contract:** 주민의 문제, 주요·보너스 필요, 허용 기능, 단서와 결과를 묶은
  퍼즐 진실. 플레이어가 그림을 제출하기 전에 잠긴다.
- **단서 계약:** 잠긴 퍼즐 진실을 대사·행동·환경 두 채널 이상으로 전달하되 정답 기능과
  사물 형태를 직접 말하지 않는 저작 규칙.
- **가시적 근거:** VLM이 특성을 판단한 실제 선, 면, 색과 배치. 그림에서 확인할 수 없는
  해석은 판정에 사용하지 않는다.
- **근거 하이라이트:** 판독 근거가 된 그림 영역을 화면에서 밝히는 연출.
- **내부 기능 태그 (affordance):** `glide`, `listen`, `connect`처럼 서로 다른 그림
  표현을 엔진의 판정 언어로 연결하는 작은 기능 단위. 플레이어에게 선택 카드로 노출하지 않는다.
- **원본 실루엣 생명화:** 공통 프레임이나 기본 몸체로 다시 그리지 않고 원본 낙서의
  외곽선·색·빈 공간을 보존한 채 움직임을 붙이는 방식.
- **Resolver:** 생성된 NPC 반응이 실제 인물·소품·위치와 확정 결과에 허용된 엔진
  명령만 사용하는지 확인하고 하나의 결과 장면으로 합치는 로컬 검증기.
- **관계 기록:** 부탁 결과를 주민과 생명체 사이의 짧은 사건으로 저장한 수집 항목.
- **수직 슬라이스:** 폭은 좁아도 부탁 관찰부터 관계 기록까지 전 층을 관통하는 최소 완결 빌드.
