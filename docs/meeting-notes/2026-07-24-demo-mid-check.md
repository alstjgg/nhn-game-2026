## TL;DR

Doodle Life는 기술 시연은 되었지만 긴 지연, 동일 그림에 대한 판정 편차, 난해한 NPC 대사,
낮은 체감 재미 때문에 이번 선택지에서 제외하기로 했다. 남은 후보는 **Apothecary와
Agent Arena 2개**다. Agent Arena는 실제 Context/MCP를 그대로 쓰는 기술 데모보다,
Prompt·Skill·Context·MCP의 개념을 게임 규칙으로 번역하는 방향으로 단순화한다. 실제 MCP
연동은 빼고, 필요하면 "열쇠 MCP" 같은 게임적 개념만 남긴다. 전투는 턴제 관전형, 맵은 분기형
자동 전진, 카드는 덱빌딩보다 가벼운 증강 선택 방식이 합의된 방향이다. 다만 실제
Prompt·Skill·Task·전투 응답 예시가 아직 얇아 두 사람의 상상이 조금씩 다르므로, 이를 먼저
구체화해야 한다(일부는 이미 [agent-arena-brief.md](../agent-arena-brief.md) 초안과
`docs/agent-arena-examples.md` 작업에 반영 중). 민서는 Apothecary 데모와 확정된 Agent
Arena PRD·super-pipeline 실행을, 윤석은 LLM 백엔드·AWS/Bedrock 가능성 조사를 맡는 흐름으로
정리됐다. 대표 컨셉은 07-25 선택을 목표로 하되, Agent Arena 데모가 아직 없어 일정은 빠듯하다.

## 1. 핵심 요약 10줄

1. Agent Arena 백엔드는 Prompt·Skill·MCP 카드, 세션 응답 저장, Provider 어댑터, SSE 등을
   시험했지만 플레이 프론트가 없고 게임 규칙과 LLM 전송 계층의 경계가 섞여 있다.
2. 두 사람은 "기술적으로 많이 넣는 것"보다 게임 반응성을 우선하기로 했고, 10초도 길 수 있으므로
   빠른 모델·낮은 추론·캐싱·로컬 LLM을 옵션으로 검토하기로 했다.
3. Doodle Life 1차 구조는 상황 전체를 LLM에 위임해 1–2분이 걸리거나 실패했고, 대사도 추상적
   번역체로 무너졌다.
4. 2차 Doodle Life는 NPC별 명확한 고민, quest-blind VLM 판독, 결정론적 판정, 병렬 NPC 반응으로
   닫힌 퍼즐 구조를 만들었지만 재미·대사·지연 문제가 남았다.
5. 같은 그림을 VLM에 넣어도 결과가 달라졌고, 결함 가능성과 "LLM 특성 또는 재미일 수 있다"는
   견해가 함께 나왔으나 결론을 내리지 않았다.
6. VLM 약 20초 대기는 너무 길다는 데 동의했으며, 걷기·이동·캐릭터 대화 같은 연출로 숨기는 방안이
   제안됐지만 확정 구현은 없다.
7. Agent Arena는 실제 MCP를 연결하지 않고 Prompt·Skill 중심으로 단순화하며, MCP는 필요하면
   게임적 "열쇠" 개념으로만 남기기로 했다.
8. Agent Arena의 합의 방향은 증강식 카드 선택, 파티 관전, 분기형 자동 전진 맵, 턴제 전투이며
   플레이어는 구성·장착·경로 선택에 개입한다.
9. Doodle Life는 고치는 비용보다 남은 두 기획에 집중하는 편이 낫다고 판단해 베이크오프 대상에서
   제외하고 Apothecary와 Agent Arena 두 트랙에 집중하기로 했다.
10. 최종 선택 전에 Agent Arena의 실제 Prompt·Skill·Task·전투 예시를 합의하고 데모를 만들어야
    하며, 07-25 선택은 준비 부족으로 지연 위험이 있다.

## 2. 주제별 상세 요약

### 2.1 Agent Arena 백엔드: 무엇이 되었고 무엇이 꼬였나

- 현재 백엔드는 Prompt 카드, Skill 카드, MCP 카드 입력과 세션별 응답 저장을 지원한다. LLM의 판단
  결과를 게임 서버나 프론트가 받아 행동하게 하는 구조이며 SSE의 필요성도 언급됐다.
- 실제 게임 프론트가 없는 상태에서 데모를 만들다 보니 전술·스킬 같은 게임 규칙이 백엔드에
  들어갔다. 두 사람은 게임 쪽에서 규칙을 처리하고 백엔드는 LLM 요청·응답에 가까운 얇은 계층이어야
  한다고 봤다.
- Context와 Memory를 실제 게임 규칙으로 쓰지 않는다면 복잡한 Agent 구조 대신 일반 API 호출로도
  충분하다는 문제 제기가 있었다. Agent 구조 유지 여부는 플레이 데모에서 실제 쓰임을 본 뒤
  결정하기로 했다.
- Provider 코드는 공용화 가능하지만 현재 응답 스키마가 Agent Arena에 맞춰져 있어 약간의 수정이
  필요하다.

### 2.2 지연·비용·모델 전략

- 정해진 상대·문제는 캐싱하고 플레이어가 만든 Agent의 판단만 실시간 호출하는 방안이 제시됐다.
- 복잡한 추론이 필요하지 않다면 더 빠르고 낮은 모델을 쓰고, 그래도 느리면 로컬 LLM을 검토하기로
  했다. 모델 다양성보다 "내 Agent를 잘 만드는 재미"와 즉각적 반응을 우선할 수 있다는 입장이다.
- 기다림을 완전히 없애지 못하면 이동 애니메이션, 던전 걷기, Agent 간 미리 생성된 대화로 숨긴다.
  사용자가 장착을 확정하기 전에는 최종 호출을 할 수 없으므로 모든 분기를 무조건 선계산하는 안은
  비용 대비 효율을 더 따져야 한다.

### 2.3 Doodle Life 평가

- 1차 "모든 상황·이벤트를 LLM이 통제"하는 구조는 1–2분 지연, 호출 실패, 과도한 코드와 데이터,
  꿈처럼 모호한 대사로 실패했다고 평가했다.
- 2차 구조는 다음과 같다.
  - World 생성 시 NPC의 외형·성격·고민을 만든다.
  - NPC마다 명확한 요청과 퍼즐 정답이 있다.
  - VLM은 정답을 모른 채 그림만 해석한다.
  - 로컬 규칙이 판정하고, 생성된 낙서와 기존 NPC의 반응을 병렬로 붙인다.
- 장점은 닫힌 판정 경계와 그림이 캐릭터로 살아나는 시각적 결과였다. 반면 NPC 요청과 대사가
  지나치게 추상적이어서 플레이어가 무엇을 그려야 하는지 알기 어려웠다.
- 같은 그림에 대한 VLM 결과가 매번 달라졌고 VLM 자체에 약 20초가 걸렸다. "LLM이라 피할 수 없는
  편차이며 재미일 수 있다"는 의견과 "랜덤 판정으로 느껴질 수 있다"는 우려가 함께 남았다.
- 더 좋은 모델과 Prompt로 대사를 고칠 수 있다는 반론은 있었지만, 실제 플레이 후 재미와 개선
  의지가 떨어졌다는 판단이 우세해 트랙을 제외했다.
- Doodle Life는 트랙 B 베이스로 자리좀봐주세요·placement를 흡수한 상태였으므로, 이 컷은 그 두
  컨셉도 함께 보류하는 것을 뜻한다.

### 2.4 Apothecary와 super-pipeline

- Apothecary PRD는 private super-pipeline 형식에 맞춰 준비됐고, 회의 중 데모 생성 작업이
  진행되고 있었다.
- super-pipeline은 PR, Commit, Issue, Review 대화에 Agent 간 의사결정 흔적을 남긴다. 파이프라인
  소스 자체를 공개하기보다 구조 설명과 작업 증거를 제출 문서에 보여주는 정도면 충분하다고
  합의했다.
- 파이프라인 저장소를 공개하기 어렵고 다른 사람이 만든 기반 코드도 포함돼 있으므로, 민서가
  로컬에서 실행해야 한다는 결론이다.
- 한 번의 super-pipeline 실행은 앞선 사례에서 약 10–12시간이 걸렸다고 언급됐다.

### 2.5 Agent Arena의 게임 설계 방향

- Prompt와 Skill은 모두 실질적으로 Prompt지만, 게임에서는 성격과 능력으로 구분해 보여준다.
- 실제 MCP 서버 연동은 구조만 복잡하게 하고 게임 이득이 불명확해 제외한다. 다만 "열쇠 MCP를
  보유하면 숨겨진 보물방을 연다"처럼 개념만 게임 규칙에 이식하는 안은 유지 가능하다.
- 카드를 덱에서 뽑는 덱빌딩 구조는 게임을 지나치게 깊게 만들 수 있어 피하고, 증강처럼 가볍게
  선택지를 제시하는 방향을 택했다.
- 플레이어는 초기 로스터 구성, Prompt·Skill 장착, 경로를 선택한다. Agent 파티는 이벤트·퍼즐·전투를
  스스로 판단하며 플레이어는 관전한다.
- 이 구조는 플레이어가 LLM에 자유 텍스트를 치지 않고 구조화된 카드로만 개입한다는 점에서
  CLAUDE.md의 **멤브레인 규칙**과 정합적이다 — 심사의 "AI 오케스트레이션 일관성" 근거로 쓸 수 있다.
- 전투는 실시간보다 턴제가 기술적으로 쉽고 관전에도 맞는다는 데 동의했다. 분기 맵은 필수에 가깝게
  봤지만, 다음 노드의 정보와 보상을 얼마나 공개할지는 결정하지 않았다.
- 초기 6개 캐릭터 중 3개를 고르는 예가 나왔고, 성장의 핵심은 큰 수치 상승보다 Prompt·Skill 조합이
  상황 판단과 파티 시너지를 바꾸는 데 있다.
- 실제 Context Compaction, Token, MCP를 그대로 재현하기보다 피로도·스트레스·환각·카드 폐기 같은
  게임 규칙으로 모사하는 방향이 현실적이라는 쪽으로 수렴했다.
- 현재 가장 큰 결손은 실제 예시다. 기본 Prompt, 추가 Prompt, Skill, Task, 턴제 전투 응답 형식이
  아직 얇아 두 사람이 서로 다른 게임을 상상한다. 이 방향의 상당 부분은 이미
  [agent-arena-brief.md](../agent-arena-brief.md) 초안과 `docs/agent-arena-examples.md`
  작업에 잡혀 있으므로, 데모보다 먼저 그 예시와 Brief를 함께 확정해야 한다.

### 2.6 배포와 LLM 인프라

- GitHub Pages는 정적이므로 별도 LLM 백엔드가 필요할 수 있다. AWS, Oracle Cloud/OCI Free
  Tier가 후보로 언급됐다.
- AWS 서버 한 달 비용을 약 18,000원으로 추산했고, 심사 기간까지 한 달 정도 띄우는 것은 감당
  가능하다는 반응이었다. 이는 회의 중 추정치이며 견적 확인은 되지 않았다.
- 이후 실제 Context·MCP 관리를 빼면 별도 Agent 서버 없이 게임 서버에서 API를 직접 호출할 수도
  있다는 의견이 나왔다. Amazon Bedrock을 중간 계층으로 쓰는 방안도 제안됐으나 두 사람 모두 사용
  경험이 없어 조사하기로 했다.
- 따라서 "AWS 상시 서버를 반드시 띄운다"는 결정은 확정되지 않았다.

### 2.7 베이크오프와 일정

- Doodle Life를 제외해 최종 비교 대상은 Apothecary와 Agent Arena 두 개로 줄었다.
- 원래 회의 당일 또는 다음 날 최종 선택하려 했지만 Agent Arena의 기획 예시와 플레이 데모가 없어
  바로 고를 수 없다고 판단했다.
- 목표 순서는 `Agent Arena 예시 확정 → Brief 확정 → PRD → super-pipeline 데모 → Apothecary와
  비교 → 하나 선택`이다.
- 대표 컨셉은 07-25 선택을 목표로 하되, 데모가 준비되지 않은 상태라 확정 기한으로 보기는 어렵다.

## 5. 참석자별 핵심 주장과 입장

### 민서

- 게임은 기술 시연이 아니라 반응성이 있는 게임이어야 하므로, Context·Memory·MCP를 실제로 유지하는
  스펙을 빼더라도 지연을 줄여야 한다고 주장했다.
- Agent Arena를 "기술 재현"이 아니라 "Agent를 만드는 게임"으로 단순화하는 설계 방향(게임화된
  MCP 개념, 증강식 선택, 분기형 자동 전진, 턴제 관전 전투)을 구체적으로 제안·정리했다.
- super-pipeline과 Apothecary 데모를 맡고, Agent Arena 기획이 확정되면 PRD와 데모도 파이프라인으로
  돌리겠다는 입장이다.

### 윤석

- Agent Arena 백엔드의 현재 구조와 Provider·세션 저장·SSE를 설명했고, 프론트가 없어서 게임 규칙이
  백엔드에 섞였음을 인정했다.
- Doodle Life 데모를 구현했고, 2차의 닫힌 판정 구조를 설명·평가했다. VLM 결과 편차는 LLM 특성상
  피하기 어렵고 오히려 재미일 수 있다는 입장을 냈지만, 20초 지연은 길다고 봤다.
- 실제 MCP 사용은 빼는 데 동의했고, 분기와 강제 카드 배분은 사용자 선택과 스트레스 관리의 재미를
  만들 수 있다고 봤다.
- Doodle Life보다 Apothecary·Agent Arena 두 기획에 집중하자는 데 동의했고, LLM 백엔드와
  AWS/Bedrock 배포 방식을 조사하겠다고 정리했다.
