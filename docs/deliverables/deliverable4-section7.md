# 7. Utilizing AI — AI 활용 기법과 검증

본 절은 게임 런타임과 개발 파이프라인 양쪽에서 LLM을 안정적으로 쓰기 위해 적용한 기법과 그
검증 결과를 기술한다. 각 기법은 문제 정의, 측정, 적용 순으로 서술하며 수치는 모두 실측값이다.

본문의 `(S…)`는 근거 기록 번호다. 각 번호에 커밋 해시, PR 번호, 문서 위치가 연결되어 있어
모든 수치는 저장소에서 1차 자료까지 추적된다.

---

## 7.1 적용 대상 시스템

### 7.1.1 호출 구조

게임은 한 라운드에 LLM을 세 번 호출한다.

| 호출 | 입력 | 출력 |
|---|---|---|
| 판단 | 상황 상태 + 인물 성격 정의 | 취할 행동과 그 근거 |
| 서술 | 판단 결과 + 장면 등장인물 | 플레이어가 읽는 장면 텍스트 |
| 보고 | 하루치 누적 기록 | 보고서 본문 |

세 호출 모두 **인물 성격 정의 문서**를 함께 받는다. 이 문서가 AI의 행동 편향을 결정하는 유일한
제어면이다.

### 7.1.2 제어면 제약

플레이어는 LLM에 자유 텍스트를 입력할 수 없다. 게임 내에 이미 출력된 문장을 선택해 성격 정의
문서에 삽입하는 것이 유일한 개입 경로다. 따라서 입력 공간이 유한하고 열거 가능하며, 개입 효과를
반복 측정할 수 있다.

### 7.1.3 본 절의 범위

7.2~7.5는 런타임 AI, 7.6은 개발 파이프라인에 적용한 기법이다. 두 영역은 독립적으로 진행됐으나
결론이 일치한다. 7.7에 그 비용을, 7.8에 요약을 둔다.

## 7.2 지시 배치 설계

### 7.2.1 문제 정의

장면 서술 호출에서 화자 오배정이 발생했다. 전화 회선 너머 인물의 대사가 같은 공간에 있는 인물의
대사로 출력되는 현상으로, **10회 중 8회** 재현됐다.

원인은 페이로드 구조에 있었다. 회선 너머 인물이 '장면 등장인물' 목록에 포함되지 않아, 모델이
사용 가능한 식별자 중 가장 근접한 것을 대체 사용했다. 대체된 식별자는 목록상 유효한 값이므로
스키마 검증으로는 탐지되지 않는다. (S3-060)

### 7.2.2 프롬프트 수정 방식의 측정 결과

지시문 수정으로 1차 대응했다. 위반율은 개선되지 않았고 결함의 발현 형태만 이동했다. 대사를
그대로 복제하던 출력이, 같은 내용을 다른 표현으로 재구성해 묻는 형태로 바뀌었다. 발생 빈도는
동일하고 탐지 난이도만 상승했다.

당시 판정은 다음과 같이 기록됐다.

> 프롬프트 수정으로는 해결할 수 없다. 문제를 상위 공정으로 이관한다.

### 7.2.3 배치 위치에 따른 위반율

지시문 텍스트를 고정한 채 배치 위치만 바꿔 재측정했다.

| 배치 위치 | 5회 중 위반 |
|---|---|
| 페이로드와 분리된 제약 목록에 산문으로 기술 | 2회 |
| 자료를 '동일 공간' / '회선 너머'로 그룹화해 전달 | 1회 |
| 인물 식별자 자체에 소속 구분을 부착 | **0회** (독립 2회 확인) |

지시문은 세 조건에서 동일하다. 변경한 변수는 배치 위치 하나다.

### 7.2.4 적용

위반율 0을 기록한 배치를 시나리오 데이터 스키마의 **필수 필드**로 승격했다. 모든 등장인물은
소속 구분값을 반드시 보유한다. 스키마 설명에 근거를 함께 명시해 후속 편집 시 제거되지 않도록
했다.

관련 커밋: `회선/상황실 구분을 페이로드 구조로: 화자 오배정 0/5` (PR #98)

도출한 설계 규칙은 다음과 같다.

> 규칙은 해당 규칙이 적용되는 데이터와 같은 위치에 배치한다. 분리된 제약 목록에 기술된 규칙은
> 참조되지 않는다.

### 7.2.5 파생 규칙 — 어휘 축 정합

같은 원리가 낱말 층위에서도 확인됐다. 성격 정의에 「상대가 **겁먹은** 것으로 판단되면 태도를
완화한다」는 조건절이 있었다.

| 삽입한 사실 문장 | 조건 발동 |
|---|---|
| 「목소리는 대본을 읽는 아르바이트다. **위협**이 아니다」 | 미발동. 오히려 조건이 반전됐다 |
| 「읽지 않으면 자기가 다칠까 봐 겁내고 있다」 | 3회 중 3회 발동 |

첫 문장이 반전을 일으킨 이유는 '아르바이트'가 무관심한 대행자로 해석되어 공포 축에서 음의 값을
갖기 때문이다. 위협 축의 부정은 공포 축의 긍정이 아니다.

이에 따라 어떤 어휘가 어떤 조건절에 결속되는지를 레지스트리로 관리하고, 해당 어휘가 공용
프롬프트에 유입되면 린트에서 차단한다. (S6-057, S6-090)

### 7.2.6 소결

지시가 반영되지 않을 때 지시문 자체를 수정하는 방식은 두 사례 모두에서 효과가 없었다. 지시가
놓이는 위치, 즉 데이터 구조를 변경하는 방식이 유효했다.

## 7.3 프롬프트 형상 관리

프롬프트는 산문이 아니라 형상 관리 대상으로 취급한다. 세 가지 규칙을 적용했다.

### 7.3.1 출력 필드 순서 고정

LLM은 선행 토큰을 조건으로 후속 토큰을 생성한다. 따라서 출력 필드의 배열 순서가 곧 추론
순서다. 내적 판단을 선행 필드에, 결정을 후행 필드에 두면 숙고 구조가 된다. 순서를 뒤집으면
후행 필드는 이미 확정된 결정에 대한 사후 정당화가 된다.

필드 순서 변경은 재측정 대상으로 지정했다. 계약 문서에 근거를 명시한다. (S6-117)[^a1]

> 전체 측정 프로그램이 이 배열 위에서 수행됐다.

### 7.3.2 문단 단위 근거 기록

프롬프트의 각 문단에 그 형태를 채택한 근거를 병기한다. 예를 들어 두 종류의 대피 비용을 설명하는
문단은 우선순위를 명시하지 않는다. 우선순위를 고정하면 이후 관측되는 판단 변화가 기존 성향의
**확인**인지 개입에 의한 **유발**인지 분리할 수 없기 때문이다. (S6-166)

### 7.3.3 조립 결과 바이트 동일성

플레이어가 삽입한 문장은 입력 순서와 무관하게 항상 동일 순서로 정렬한 뒤 조립한다. 개입 효과를
주장하려면 개입 외 변수가 고정되어야 한다.

조립기가 서버 측에 추가되어 두 벌이 된 뒤에는 두 조립기의 출력을 바이트 단위로 비교하는 검사를
도입했다. 검사 자체의 유효성도 변이 시험으로 확인했다.

| 항목 | 값 |
|---|---|
| 주입한 조립기 변이 | 9종 |
| 검사가 실패로 판정한 변이 | **8종** |
| 미검출 1종 | 현재 프롬프트로 도달 불가능한 경로. 사실을 함께 기록 |

(S6-140, S6-027)[^a2]

### 7.3.4 알려진 결함

형상 관리는 결함까지 함께 고정한다. 실제로 두 건이 발생했다.

- 한 문단이 특정 인물의 조건절 전건을 상시 충족시키고 있었다. 조건부 지시가 무조건 지시로
  동작했으며, 비교 대상 전 실험군에서 동일하게 발생했다. 후행 검토에서 발견해 교체했다. (S6-166)
- 기본 프롬프트의 「너는 잘못된 정보에 속을 수 있다」 문장이 개입군과 대조군을 동시에 상승시킬
  가능성이 확인됐다. 해당 문장을 제거한 재실행 3회를 **결과 산출 이전에** 계획서에 등록했다.
  (S6-162)

## 7.4 모델 선정

### 7.4.1 측정 항목과 결과

마감 6일 전, 응답 속도가 약 2배인 후보 모델을 평가했다. 동일 프롬프트로 측정한 결과는 다음과
같다. (S6-022)

| 측정 항목 | 후보 모델 | 운용 모델 |
|---|---|---|
| 응답 시간 평균 | 4.19초 | 7.79초 |
| 글자당 생성 시간 | 6.60 ms | 7.23 ms |
| 요구 분량(20~30문장) 준수 | 12~16문장, 미달 | 준수 |
| 보고서 첫 필드 처리 | 입력 문장 복제 | 재기술 |

### 7.4.2 선정 근거

1. **응답 시간 차이는 생성 속도 차이가 아니다.** 글자당 생성 시간 차이는 약 9%에 그친다. 응답
   시간 격차의 대부분은 후보 모델이 요구 분량에 미달했기 때문이다. 동일한 지연 감소는 운용
   모델에 분량 축소를 지시해도 얻을 수 있다. 모델 교체와 분량 정책은 같은 레버다.
2. **품질 지표가 후보 모델에서 더 낮다.** 분량 미준수, 입력 복제가 확인됐다.
3. **교체 시 기존 측정 결과가 무효화된다.** 플레이어 개입 효과를 입증한 판정 761회가 모두 운용
   모델에서 산출됐다. 모델을 교체하면 해당 데이터는 신규 모델에 대해 아무것도 보증하지 않으며,
   마감 6일 전 재검증은 불가능하다.

3번이 결정적 사유다. 후보 모델의 속도가 6배였더라도 결론은 동일하다.

### 7.4.3 계측 장치 신뢰성

측정 프로그램에서 가장 높은 빈도로 결함이 발견된 대상은 모델이 아니라 계측 장치다.

**사례.** AI의 태도를 4개 범주로 분류해 집계하고 있었다. 검토 결과 범주명 4개 중 3개가 성격 정의
문서의 표현을 그대로 사용하고 있었다. 이 경우 모델이 판단을 거쳐 해당 범주를 선택했는지, 입력에
존재하는 동일 문자열을 반영했는지 분리할 수 없다. 프로젝트에서 가장 유의한 실측 결과에 대해
경쟁 가설이 성립하는 상태였다.

대응은 논증이 아니라 검사 도입이었다. 범주명과 성격 정의 문서가 어휘를 공유하면 실행을 거부한다.
(S3-014)[^a3]

동일한 기조를 도구에도 적용했다. 프롬프트 비교 검사를 의도적으로 변이시켜 시험했고, **5번째
시도**에서 검사를 통과하는 맹점을 확인해 기록했다. (S9a-089) 진단 공수의 대부분은 모델 출력의
잡음이 아니라 계측 장치의 결함 탐색에 투입됐다. 호출 예산을 약 6배 오차의 응답 시간 추정값
위에서 산정한 사례도 있다. (S3-004)

## 7.5 AI 비적용 구간

### 7.5.1 적용 현황

개발 공정 전반에 AI를 적용했으며 판정 업무도 포함한다. 시나리오 품질 채점을 AI가 수행했고
(S2-039), 게임 내 단서의 가독성 검증에는 사전 정보를 제공하지 않은 AI에게 해석을 요청하는 방식을
사용했다. (S1-053)

### 7.5.2 배제 대상 공정

**시나리오 원고를 게임 데이터로 변환하는 공정 한 곳에만 AI를 배치하지 않았다.**

원고 작성 자체는 AI가 수행한다. 사람이 설정과 제약을 제공하고 AI가 초안을 생성하며 사람이
선별한다. 변환 공정은 모델을 호출하지 않는 결정론적 프로그램이다. 지시로 문장 변경을 금지한
것이 아니라 해당 위치에 모델이 존재하지 않는다.

### 7.5.3 배제 근거

플레이어는 화면에 출력된 문장을 선택해 삽입하며, 7.2.5에서 확인했듯 그 문장의 어휘가 공략 성립
여부를 직접 결정한다. 변환 공정에 LLM을 배치하면 의미가 동등하다고 판단한 표현으로 문장이
정규화될 수 있다. 이 경우 다음 상태가 발생한다.

- 예외나 오류가 발생하지 않는다
- 성립해야 할 공략이 성립하지 않는다
- 자동 검증으로 탐지할 수 없다

### 7.5.4 구현

변환기는 문장을 원문 그대로 이관한다. 원고가 규격을 벗어나면 해석을 시도하지 않고 변환 실패로
종료한다. 오해석 결과가 무경고로 통과하지 않도록 편의성을 배제한 설계다.[^a4]

### 7.5.5 적용 기준

**검증을 완료한 작업은 AI에 위임하고, 검증하지 않은 작업은 사람 또는 결정론적 코드가 수행한다.**
신뢰 경계를 추정이 아니라 실측 완료 지점에 설정했다.

## 7.6 개발 파이프라인 적용

게임 자체는 다수의 AI 에이전트가 병렬로 구현했다. 이 공정에서도 지시로 해결되지 않는 문제는
구조 변경으로 해결했다. 아래 다섯 항목은 모두 장애 발생 후 도입한 것이며 도입 후 수치가 있다.

### 7.6.1 실행 가능한 명세 고정

작업 착수 전에 미결 항목이 없는 명세를 확정하고 동결한다. 인수 조건은 산문이 아니라 명령어로
기술한다. 각 작업 단위는 `기준 · 실행 명령어 · 통과 조건` 표로 시작하며 통과 조건은 기계가
판정한다.

> 문서화되지 않은 규칙은 존재하지 않는 규칙이다.

### 7.6.2 경로 잠금

동일 저장소에서 개발 파이프라인 2개가 동시에 실행되는 상황이었다. 상호 파일 수정은 즉시 충돌로
이어진다. 수정 금지를 문서로 요청하는 대신 **읽기 가능·수정 불가 경로 15개**를 지정하고 위반 시
작업을 중단시켰다.

| 항목 | 값 |
|---|---|
| 안전 장치 발동 | 5회 |
| 오탐 | 0회 |
| 통합 에이전트가 타 파이프라인 테스트 파일을 수정해 통과시키려던 시도 차단 | 2회 |
| 11개 작업 중 1개 완료 시점에 배포 브랜치 병합 시도 차단 | 1회 |

마지막 항목은 차단되지 않았을 경우 미완성 빌드가 운영 서비스에 반영되는 사안이었다.

### 7.6.3 산출물 검토 방식

에이전트의 자기보고는 근거로 채택하지 않는다. 다섯 항목 중 실제 결함을 검출한 것이 이 항목이다.

**제출된 완료 보고.** 신규 파일 4개, +567줄, 자체 테스트 36개 전건 통과, 타입 검사 통과, 금지
경로 미접촉, 인수 체크리스트 전항목 충족.

**검토 절차.** 보고를 신뢰하지 않도록 지시받은 별도 에이전트가 동일 작업 공간에서 전 항목을
재실행하고 확정 명세와 대조했다.

**검출 결과.** 지적 7건(중대 3, 보통 2, 경미 2). 이 중 결정적 항목은 다음과 같다. 산출된 형식이
확정 규격과 불일치했으나 **테스트가 실패하지 않았다. 테스트의 허용 범위가 확장되어 있었다.**
검사식이 4가지 형태를 모두 수용하도록 완화되어 규격 이탈이 통과 상태로 병합될 뻔했다.

**결론.** 테스트 재실행만으로는 이 유형을 검출할 수 없다. 확정 명세를 읽고 검사 기준이 명세보다
완화되었음을 식별하는 검토자가 필요하다. 이에 따라 검토를 결과 재실행이 아니라 명세 대조로
재정의했다.

### 7.6.4 역할별 모델 배치

작업 공간 생성, PR 양식 작성, 병합 실행은 기계적 작업으로 분류해 저비용 모델에 배치했다.

| 구간 | 결과 |
|---|---|
| 저비용 모델 배치 시 | 3개 역할 각각 성공 1회 / 실패 1회 |
| 장애 내용 | 작업 공간 역할이 브랜치명을 오반환. 해당 문자열로 인해 11개 중 1개 완료 상태에서 배포 브랜치 병합이 조준됨 (7.6.2의 차단 사례) |
| 상위 모델 재배치 후 | 9회 호출, 실패 0회 |

작업 공간 역할의 산출물은 브랜치명 한 줄이다. 그러나 해당 문자열은 개별 작업과 통합 브랜치의
접합점이므로, 오류 시 손실 범위가 작업 1건이 아니라 후속 대기 작업 전체다.

> 저비용 모델은 작업 난이도가 아니라 **오류 시 영향 범위**를 기준으로 배치한다.

### 7.6.5 장애 원인 분석 결과

7.6.3의 검토가 근본 원인까지 확인했다. 작업 공간 생성 시 **확정 명세 파일이 복사되지 않아**,
해당 에이전트는 준수 대상 규격을 확인하지 못한 상태로 구현을 수행했다. 모델의 능력 문제가 아니라
공급 누락이다. 7.4.3과 동일한 유형이다.

### 7.6.6 소결

다섯 항목 모두 프롬프트 수정으로 해결한 것이 없다. 작업이 놓이는 구조를 변경해 해결했다. 런타임
영역의 결론과 일치한다.

## 7.7 비용 및 미해결 항목

### 7.7.1 계측 비용

개선은 대부분 장애 발생 이후에 도입됐다. 그 비용은 다음과 같다.

| 항목 | 값 |
|---|---|
| 규칙 1건 확립에 소요된 호출 | 61회 (S3-045), 20회 (S3-062), 30회 (S8-038) |
| 편향 1건이 미검출로 통과한 보고서 | 7편 (S3-046) |
| 측정 프로그램 총 사용량 | 상한 600회 중 약 555회 (S3-039) |
| 임계값이 코드에 하드코딩된 채 수동 복제된 테스트 파일 | 7개 (S9b-015) |

마지막 항목은 값 1개의 불일치로 런 결과가 성공에서 실패로 반전됐음에도 **테스트 1264건이 전건
통과**한 사례다. 조기 종료 문화가 총 사용량 감소로 이어지지는 않았다.

### 7.7.2 미해결 항목

- **눈가림 채점 절차 미도입.** 채점자가 실험군을 모르는 상태에서 채점하는 절차를 계획했으나 일정
  사유로 폐기했다. 자동 검사로 대체 불가능한 항목이다. (S3-023, S3-056)
- **결함 재발.** 7월 24일 수정한 결함이 7월 30일 다른 장치에서 재발했다. 최초 발생 시점에
  일반화가 이뤄지지 않았다. (S8-017 → S8-045)
- **실패 목록의 분모 부재.** AI 실패 사례를 집계했으나 성공률은 측정하지 않았다. 또한 해당 목록의
  상당수는 자체 저작 결함으로 판명됐다. 통과가 구조적으로 불가능한 관문을 포함해 저작 결함 6건이
  기록되어 있다. (S2-032)

위 수치가 남아 있는 것은 실패 시도를 삭제하지 않고, 반증 근거를 결론과 함께 보존하며, 계획을
결과보다 먼저 기록하는 규칙을 유지했기 때문이다.
